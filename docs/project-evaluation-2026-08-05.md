# TextAudio 프로젝트 종합 평가 (2026-08-05)

## 한 줄 요약

1인 개발 PWA 치고 이례적으로 잘 관리된 프로젝트. 규모(백엔드 ~4,600줄 + 프론트 ~9,400줄 + CSS ~4,300줄, 424커밋)에 비해 구조·테스트·배포 파이프라인이 탄탄하고, 가장 큰 약점은 기능이 빠르게 붙으면서 생긴 레거시 이중화와 일부 비대해진 파일들이다.

---

## 잘된 점

### 1. 아키텍처 규율 (A)
- 백엔드가 도메인별 라우트 파일(tts/library/news/folders/auth...)로 깔끔히 분리돼 있고, TTS는 어댑터 패턴(`tts_providers/`)으로 공급자 교체가 가능한 구조. edge-tts ↔ Google 전환을 실제로 겪으면서 검증된 추상화라 과잉 설계가 아님.
- 프론트는 View/State/Logic 파일 분리 컨벤션이 전체에 일관 적용됨. 컨벤션이 문서(`.claude/development-guidelines.md`)로도 존재해서 유지 가능성이 높음.

### 2. 테스트와 검증 문화 (A-)
- 282개 테스트 전부 통과, 커버리지 88%. 사이드 프로젝트에서 이 수치는 드묾.
- 버그 수정 시 재현 테스트를 먼저 쓰는 패턴이 커밋 이력에 실제로 남아 있음.
- 다만 프론트엔드는 자동화 테스트가 0. 최근 프로필 탭 침범·chevron 크래시 같은 버그가 전부 프론트에서 났다는 점을 보면 여기가 실질적 리스크.

### 3. 운영 품질 (B+)
- CI/CD(GitHub Actions → Fly.io), sw.js 캐시 버전 관리, safe-area/풀투리프레시 같은 iOS PWA 특유의 함정을 하나하나 잡아온 이력이 코드 주석에 잘 남아 있음. "왜 이렇게 했는지"를 설명하는 주석 품질이 특히 좋음 — 6개월 뒤의 본인이 읽어도 이해 가능한 수준.
- 시크릿은 env로만 관리(git 추적 없음), CORS는 명시적 origin 화이트리스트, 관리자 API는 `require_admin_user` 게이트. 기본기는 갖춰짐.

### 4. 제품 감각 (B+)
- 문서→오디오북이라는 코어에 뉴스 브리핑, 라이브러리(서점), 클라우드 동기화가 자연스럽게 붙었고, iOS 네이티브 관성(액션시트, large title, 시트 스크롤 규칙)을 꾸준히 따라가서 PWA인데 앱처럼 느껴짐.

## 약점과 리스크

### 1. 레거시 이중화 (가장 큰 기술부채)
`frontend/static/js/` + `app.js`에 바닐라 JS 구현이 약 3,700줄 남아 있음. Vue SPA가 메인인데 정적 `index.html` 경로가 여전히 이걸 참조. 기능 수정 시 "두 군데 고쳐야 하나?"라는 혼란의 근원이고, sw.js가 이 레거시 파일들을 아직 캐싱 목록에 넣고 있음. **레거시 진입점을 완전히 제거하거나, 최소한 캐시 목록에서 빼는 정리가 필요.**

### 2. 비대해진 파일
- `routes/tts.py` 653줄, `Generation_Logic.vue` 684줄, `Reader_Logic.vue` 538줄, `AudioList_Logic.vue` 514줄. 아직 감당 가능하지만 다음 기능 추가 때 분리 시점을 넘기면 급격히 나빠지는 구간.
- `style.css` 3,905줄 단일 파일 — 같은 셀렉터(`.app-header`)가 파일 내 여러 곳에서 재선언되며 "어느 규칙이 이기는지" 주석으로 설명해야 하는 상태는 이미 경고 신호.

### 3. 프론트엔드 테스트 부재
최근 실제 프로덕션 크래시 2건(멀티루트 v-show, lucide chevron)이 모두 프론트. Vitest + 컴포넌트 테스트 몇 개만 있어도 이 클래스의 회귀는 잡힘. 지금은 매번 브라우저 수동 검증에 의존.

### 4. 외부 의존 리스크
- Edge-TTS는 비공식 API라 언제든 끊길 수 있음(이미 Render에서 연결 불안정 경험). Google TTS 어댑터가 백업으로 있는 건 잘한 것.
- Supabase 단일 의존 — 백업/내보내기 전략이 코드상 안 보임.

### 5. 미완 항목
태스크 목록 기준: 관리자 대용량 백그라운드 작업 실사용 검증, 백그라운드 작업 폴더 배치, 구글 클라우드 프로젝트 통합이 남아 있음.

## 작업 중 발견된 프로덕션 버그 (해결됨)

"서점 → 서재에 저장" 기능이 프로덕션에서 완전히 동작하지 않았다. `GET /api/library/saves`가 로그인한 모든 사용자에게 500을 돌려주고 있었다. 원인이 **두 개 겹쳐** 있었다.

**원인 1 — DB 권한 누락.** `library_saves` 테이블에만 DML 권한이 아무 롤에도 부여돼 있지 않았다(`42501 permission denied`). 다른 테이블(audiobooks, users, folders, push_subscriptions)은 전부 정상. 게다가 이 테이블만 RLS가 꺼져 있고 정책도 없었다. 프로덕션 DB에 적용:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON public.library_saves TO service_role;
ALTER TABLE public.library_saves ENABLE ROW LEVEL SECURITY;
```

anon/authenticated에는 권한을 주지 않았다 — 백엔드가 service_role로만 접근하고, 브라우저는 Supabase에 직접 붙지 않기 때문이다. 이 테이블은 RLS 정책이 없으므로 anon에 권한을 열었다면 전 사용자의 저장 목록이 노출됐을 것이다.

**원인 2 — 라우트 순서 버그** (커밋 `a55da2c`). 권한을 고친 뒤에도 500이 계속됐고, 에러 메시지가 `invalid input syntax for type uuid: "saves"`로 바뀌면서 드러났다. `@router.get("/api/library/{audiobook_id}")`가 `/api/library/saves`보다 먼저 등록돼 있어 `"saves"`가 audiobook_id로 잡히고 있었다. FastAPI는 등록 순서대로 매칭하므로 **이 엔드포인트는 추가된 이후 한 번도 동작한 적이 없었다.** 순서를 바꾸고 회귀 테스트를 추가했다.

검증: 프로덕션에서 인증 없이 401(= saves 핸들러에 도달), 인증 후 200 `{"library":[]}`. DB 레벨에서 저장/저장취소 왕복과 반복 저장 멱등성도 확인했고 테스트 데이터는 모두 정리했다.

재발 방지로 `docs/SUPABASE_SETUP.md`에 `library_saves` 섹션을 추가했다 — 애초에 이 테이블만 셋업 문서에 없었던 것이 누락의 원인이었다.

**종합: B+ ~ A-.** 코드가 "빨리 만든 사이드 프로젝트"가 아니라 "운영하는 제품"의 형태를 갖추고 있고, 약점들도 방치된 게 아니라 인지된 상태(주석·태스크에 기록됨)라는 점이 좋다. 레거시 정리와 프론트 테스트만 채우면 안정적으로 A.
