# 대용량 합성 작업이 통째로 날아가거나 고아 레코드를 남김

## 증상

관리자 대용량 백그라운드 합성 기능을 실제로 뜯어보니, 코드는 동작하지만 몇 가지
정합성·신뢰성 구멍이 있었다(사용자가 겪은 게 아니라, 기능을 점검하며 발견).

## 원인 (네 가지가 겹쳐 있었다)

1. **동시성 제한이 잘못된 단계에 걸림**: `large_admin_upload_lock`은 파일
   업로드(텍스트 추출) 동안만 걸렸다. 실제로 CPU를 오래 쓰는 건 TTS 합성인데,
   여기엔 아무 제한이 없어 여러 대용량 합성 작업이 동시에 돌 수 있었다.
2. **결과 저장 순서가 거꾸로**: `_store_background_audiobook`이 `audiobooks`
   DB 행을 먼저 만들고 그 다음 Storage에 mp3·문장 JSON을 올렸다. 업로드가
   중간에 실패하면 파일 없는 행이 고아로 남는다.
3. **부분 실패가 전체를 날림**: 5묶음을 `asyncio.gather`로 병렬 처리하는데,
   청크 하나가 재시도(3회)를 다 소진하면 나머지 묶음이 멀쩡히 끝났어도 문서
   전체가 실패로 끝났다. 몇 시간짜리 작업이 이렇게 날아갈 수 있었다.
4. **재시작 시 중복 재개 가능성**: 배포 중 이전·새 프로세스가 잠깐 겹치면,
   같은 `queued`/`processing` 행을 두 프로세스가 동시에 재개해 같은 작업을
   두 번 처음부터 합성하고 `audiobooks`에 중복으로 저장할 수 있었다.

## 해결

1. `background_synthesis_lock`을 추가해 합성 작업 자체를 동시 1개로 제한하고,
   확인+큐 등록을 같은 락 안에서 원자적으로 처리(`main.py`).
2. `_store_background_audiobook`의 순서를 뒤집어 Storage 업로드를 모두 마친
   뒤에만 DB 행을 만들고, 문장 JSON 업로드가 실패하면 이미 올라간 mp3를
   `storage.remove()`로 되돌린다.
3. `process_background_synthesis_task`를 "all or nothing" 전체 재시도 루프로
   바꿨다 — 실패하면 문서 전체를 처음부터 최대 3번 다시 돌린다(시도 사이
   30·60초 대기). 부분 재시도·체크포인트 인프라를 새로 만드는 것보다 단순하고,
   원문이 완료 전까지 DB에 남아 있어 항상 안전하게 재시도할 수 있다.
4. `resume_background_synthesis_jobs`에 조건부 update(`eq("status", 이전_상태)`)로
   선점(claim) 로직을 추가했다 — 두 프로세스가 동시에 재개를 시도해도 실제로
   상태를 바꾸는 데 성공한 쪽만 진행한다.

각 안전장치는 추가 후 일부러 코드를 원상태로 되돌려(재시도 횟수를 1로,
선점 로직을 제거) 대응 테스트가 실제로 실패하는 것을 확인한 뒤 다시 적용했다.

## 교훈

"기능이 동작한다"와 "기능이 신뢰할 수 있다"는 다르다. 특히 몇 시간씩 걸리는
백그라운드 작업은 (a) 동시에 몇 개까지 허용할지, (b) 부분 실패를 어떻게
다룰지, (c) 프로세스 재시작·겹침을 어떻게 다룰지를 처음부터 설계에 넣어야
한다. 이 넷 다 "정상 경로"만 테스트해서는 절대 드러나지 않는다.
