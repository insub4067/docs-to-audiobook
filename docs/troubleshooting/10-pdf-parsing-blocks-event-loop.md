# 큰 파일 업로드 중 다른 사용자 요청이 전부 멈춤

## 증상

[09번 문서](09-pdf-garbled-extraction.md)의 PDF는 원본이 175MB대였다. 당시
관리자 업로드 상한(`MAX_ADMIN_UPLOAD_BYTES`)이 50MB라 그대로는 올릴 수 없었고,
상한을 올리는 김에 코드를 다시 보다가 더 심각한 문제를 발견했다: 이런 대용량
파일을 파싱하는 동안 이 서비스가 단일 인스턴스·단일 이벤트 루프로 도는 구조라,
그 시간 동안 다른 모든 사용자(일반 사용자 포함)의 요청이 전부 멈출 수 있는
구조였다.

## 원인

`/api/upload` 핸들러(`main.py`)가 `text = extract_text(temp_path, safe_name)`를
`await` 없이 **동기 호출**하고 있었다. `extract_text`는 `pypdf`로 PDF를
파싱하는 순수 동기 함수라, 이 호출이 끝날 때까지 FastAPI의 단일 이벤트 루프가
완전히 블로킹된다. 업로드 자체(`save_upload_limited`)는 이미 청크 단위로 디스크에
스트리밍해 메모리 안전했지만, 그 다음 파싱 단계는 안전하지 않았다.

파일이 클수록(특히 관리자 대용량 경로) 파싱 시간이 길어지고, 그 시간만큼
서비스 전체가 응답을 못 한다 — 50MB에서도 잠재적으로 있던 문제인데, 상한을
올리면서 실제 영향이 훨씬 커질 뻔했다.

## 해결

`text = await asyncio.to_thread(extract_text, temp_path, safe_name)`로 바꿔
파싱을 별도 스레드로 오프로드했다(관리자 경로·일반 경로 둘 다). GIL 때문에
연산 자체가 더 빨라지진 않지만, `await` 지점에서 이벤트 루프가 다른 코루틴
(다른 사용자의 대기 중인 요청)에 제어를 넘길 수 있게 돼, 파싱 중에도 서비스
전체가 멈추지는 않는다.

## 교훈

`async def` 핸들러 안이라고 해서 그 안의 모든 호출이 논블로킹인 건 아니다.
동기 라이브러리(pypdf, PIL 등 CPU 바운드 작업)를 `await` 없이 직접 호출하면
단일 이벤트 루프 전체가 멈춘다. 특히 이 프로젝트처럼 인메모리 전역 상태 때문에
단일 인스턴스로 묶여 있는 구조에서는, 한 요청의 무거운 동기 작업이 사실상
전체 서비스 장애로 번질 수 있다는 걸 항상 의심해야 한다.
