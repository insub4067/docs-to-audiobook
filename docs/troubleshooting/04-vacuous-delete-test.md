# 통과하는 테스트가 실제로는 아무것도 검증 안 함

## 증상

`test_delete_audiobook_success`가 항상 초록불이었는데, 테스트 스위트를 리뷰하는
과정에서 이 테스트가 실제로 소유권 검증 로직을 전혀 실행하지 않는다는 게 드러났다.

## 원인

테스트는 Supabase mock 체인을 `.eq().single()`로 설정했는데, `main.py`의 실제
코드는 `.eq("id", ...).eq("user_id", ...)`(단일 소유권 필터가 아니라 두 번째
`.eq()`로 소유자 검증)를 호출하고 있었다. 체인이 어긋나 있으니 실제 코드가 받는
건 설정 안 된 `MagicMock` — 이건 기본적으로 참(truthy)으로 평가된다. 그 결과
"404를 던져야 하는 조건(소유자 아님)"이 코드에서 아예 실행되지 않았는데도, mock이
뭘 리턴하든 상관없이 테스트가 통과했다.

직접 mock 체인을 재구성해 `not found`가 항상 `False`로 평가된다는 걸 확인해
이 사실을 증명했다.

## 해결

mock을 실제 코드 경로(`.eq().eq()`, `data`를 dict가 아니라 list로)에 맞게
고쳤다. 그리고 이 수정이 진짜 의미 있는지 검증하기 위해, `main.py`의 실제 소유권
필터를 일부러 깨뜨리고 형제 테스트인 `test_delete_audiobook_forbidden`이 실제로
실패하는지(200이 나오는지) 확인한 뒤 원복했다.

## 교훈

Mock 체인이 실제 코드의 호출 순서·인자와 정확히 일치하는지 항상 대조해야 한다.
어긋난 mock은 "테스트가 통과하니 안전하다"는 거짓 신뢰를 준다. 이 사건 이후로
이 프로젝트에서는 새 테스트를 작성하면 관련 프로덕션 코드를 일부러 깨서 테스트가
실제로 실패하는지 확인하는 절차를 기본으로 삼았다.
