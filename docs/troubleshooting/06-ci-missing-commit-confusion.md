# CI가 계속 실패하는데 로컬은 통과함

## 증상

연속 3개 커밋에서 GitHub Actions의 `test` job이 계속 빨간불이었다. 그런데
정확히 같은 코드를 로컬에서 `pytest`로 돌리면 전부 통과했다.

## 원인 진단 과정 (오판 하나 포함)

1. GitHub Actions 로그 요약만 보고 "`python -m pip install --upgrade pip` 단계에서
   실패"라고 처음에 잘못 판단했다. 실제로는 워크플로의 `run:` 블록이 pip
   install부터 `pytest -v`까지 **한 스텝**이라, GitHub UI가 그 블록의 첫 줄을
   스텝 이름으로 표시할 뿐이었다 — 진짜 실패는 맨 마지막에 도는 pytest였다.
2. 실제 pytest 로그(사용자가 캡처해 공유)를 보고서야 진짜 원인이 드러났다:
   `main.py`가 `process_synthesis_task`에서 호출하는 함수를 `synthesize_document`
   → `synthesize_document_to_file`로 이미 리팩터링해서 **커밋까지 했는데**,
   대응하는 테스트 수정은 로컬 워킹 디렉터리에만 남기고 **커밋을 깜빡했다**.
   GitHub(원격)에는 옛 함수명을 patch하는 낡은 테스트가 남아 있었고, patch
   대상이 존재하지 않으니 아무 효과가 없어 실제 코드가 그대로 실행되며 실패했다.
3. 로컬에서는 항상 통과했던 이유: 로컬 워킹 디렉터리에는 이미 고쳐진(하지만
   미커밋 상태인) 테스트가 있었기 때문에, 로컬 실행과 CI(원격 HEAD) 실행이
   서로 다른 코드를 테스트하고 있었다.

## 해결

로컬에 있던 미커밋 테스트 수정사항(4개 파일)을 검토해 그대로 커밋·푸시했다.
CI가 다시 통과했다.

## 교훈

- GitHub Actions에서 여러 명령을 하나의 `run:` 블록에 몰아넣으면, UI에 보이는
  "실패한 단계 이름"이 실제 실패 지점을 가리키지 않을 수 있다. 실제 로그를
  봐야 한다.
- "로컬은 통과하는데 CI는 실패한다"는 항상 "로컬과 CI가 다른 코드를 보고
  있다"는 뜻일 수 있다는 걸 의심해야 한다 — `git status`로 미커밋 변경사항부터
  확인한다.
- 이 세션 자체가 여러 병렬 세션이 같은 워킹 디렉터리를 동시에 쓰는 상황이었다.
  다른 세션의 미완료 작업(uncommitted 파일)을 실수로 건드리거나 무시하지
  않도록, 커밋 전에는 항상 `git status`로 "내가 실제로 만진 파일"만 정확히
  골라 스테이징해야 한다.
