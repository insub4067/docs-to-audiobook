# 관리자 대용량 문서 백그라운드 처리 PRD

## 문제

관리자가 10MB를 넘는 PDF를 올리면 텍스트 추출과 오디오 합성이 길어져 브라우저를 닫거나 iOS PWA가 종료될 때 결과를 잃을 수 있다. 대용량 문서는 업로드가 끝난 뒤 서버가 사용자 대신 추출·합성·보관까지 완료해야 한다.

## 목표

- 관리자(현재 `ADMIN_EMAILS`)의 10~50MB 파일을 서버 백그라운드 작업으로 처리한다.
- 업로드 전송이 완료되면 즉시 “서버에서 백그라운드 생성이 시작되었습니다. 완료되면 보관함에 저장됩니다.” 토스트를 표시한다.
- 브라우저를 닫아도 결과를 `audiobooks` 보관함에 저장한다.
- 배포·서버 재시작 뒤 `queued`/`processing` 작업을 재개한다.
- 대용량 작업은 최대 5개 합성 묶음으로 처리한다. 관리자 글자 수는 고정 상한 대신, 요청 시점의 실제 여유 디스크를 재서 판단한다(`_has_enough_disk_for_synthesis`) — 고정 숫자는 디스크 사용량이 변하는 상황을 반영 못 하고, 안전할 것 같은 값을 추측하는 것보다 실제로 재는 게 정확하다.

## 비목표

- 브라우저가 닫힌 뒤 아직 전송되지 않은 파일 바이트를 업로드하는 기능
- 일반·익명 사용자의 영속 백그라운드 처리
- 여러 대 서버/분산 큐
- 완료 오디오의 자동 만료 정책 변경

## 사용자 흐름

> 아래는 실제 구현 기준이다. 원안은 "업로드 전송 완료" 시점에 곧바로 백그라운드가
> 시작된다고 가정했지만, 실제로는 기존 앱의 업로드→미리보기→설정→생성 흐름을
> 그대로 유지하고 **"생성" 버튼을 누르는 시점**(`/api/synthesize` 호출)에 대용량
> 여부를 판단해 백그라운드로 전환한다. 관리자도 음성·속도·피치를 미리 확인하고
> 조정할 시간이 필요하기 때문이다. "브라우저를 닫아도 결과를 잃지 않는다"는
> 핵심 목표는 그대로 달성된다.

1. 관리자가 10~50MB 파일을 선택하면 서버가 텍스트만 추출해 미리보기를 보여준다(`/api/upload`, 기존 흐름과 동일).
2. 관리자가 모달에서 음성·속도·피치를 설정하고 "오디오북 만들기"를 누른다(`/api/synthesize`).
3. 글자 수가 일반 상한(10만 자)을 넘으면 서버가 대용량 경로로 판단해 `background_synthesis_jobs`에 추출된 텍스트와 함께 `queued`로 기록하고, 응답에 `background_started: true`를 실어 즉시 돌려준다.
4. UI는 토스트를 띄우고 생성 중 표시를 지운다. 이 요청에 대해서는 모달을 다시 열거나 폴링하지 않는다.
5. 백그라운드 워커가 저장해둔 텍스트로 구조화, 5묶음 TTS, MP3 결합을 수행한다.
6. 서버가 MP3·문장 JSON을 Storage에 올리고 `audiobooks` 행을 만든다. DB의 원문(`source_text`)은 즉시 `NULL`로 지운다.
7. 사용자가 다시 접속하면 기존 클라우드 동기화로 완성본을 보관함에서 본다.

## P0 요구사항

### 권한 및 시작

- 서버가 관리자 권한을 재검증한다. 클라이언트 `is_admin` 값은 권한 근거가 아니다.
- 10MB 초과 파일만 영속 작업을 사용한다. 10MB 이하 기존 미리보기·모달 흐름은 유지한다.
- 대용량 요청에는 업로드 시점의 `voice`, `rate`, `pitch`를 Form으로 보낸다.
- 관리자 대용량 작업은 동시에 하나만 실행한다. 추가 요청은 429와 한국어 안내를 반환한다.

### 저장 및 복구

- `background_synthesis_jobs`에 `id`, `user_id`, `source_text`, 제목, 음성 설정, 상태, 오류, 결과 `audiobook_id`, 시각을 저장한다.
- 원본 파일이 아니라 업로드 단계에서 이미 추출된 텍스트(`source_text`)를 저장한다. 원본 PDF를 Storage에 올렸다가 워커가 다시 내려받아 재추출하는 구조보다 단순하고, 텍스트가 PDF보다 훨씬 작아 대용량 Storage 업로드 신뢰성 문제도 피한다.
- 작업이 **완료**되면 DB의 `source_text`를 즉시 지운다. **실패**한 작업은 디버깅·재시도를 위해 `source_text`를 남겨둔다 — 자동 재시도 대상이 아니므로(재개는 `queued`/`processing`만 대상) 남겨둔다고 자동으로 다시 실행되지 않는다.
- 관리자 대용량 **업로드**(텍스트 추출)와 **합성 작업 실행**은 서로 다른 락으로 각각 동시 1개로 제한한다. 실제 CPU를 오래 쓰는 쪽은 합성이므로, 이미 진행 중인 작업이 있으면 새 합성 요청은 즉시 429로 거부한다.
- 서버 시작 시 `queued`·`processing`을 조회해 재개한다. 재개는 원문부터 다시 합성하므로 진행률은 0%부터 다시 올라간다.
- 재개 전에 `status`가 그대로일 때만 `processing`으로 바꾸는 조건부 update로 각 작업을 선점(claim)한다. 배포 중 이전·새 프로세스가 잠깐 겹쳐 같은 행을 동시에 재개 시도해도, 실제로 상태를 바꾸는 데 성공한 쪽만 진행하고 나머지는 조용히 건너뛴다.
- **문서 전체 재시도(all or nothing)**: 5묶음 병렬 처리는 asyncio.gather를 쓰므로 청크 하나가 재시도(3회)를 다 소진하면 나머지 묶음이 끝났어도 전체가 실패한다. 부분 재시도·체크포인트 인프라를 따로 만드는 대신, 실패하면 문서 전체를 처음부터 최대 3번 다시 돌린다(시도 사이 30·60초 대기). 몇 시간짜리 작업이 통째로 날아가는 것보다, 드문 실패를 자동으로 다시 시도하는 편이 단순하고 충분하다.

### 결과

- 서버가 완료 MP3와 문장 JSON을 기존 `audiobooks` 버킷의 사용자 경로에 업로드한다.
- 완료 후 `audiobooks` 행을 만들고 작업 상태를 `completed`로 갱신한다.
- 실패 시 `error` 상태와 사용자에게 보여줄 한국어 오류를 기록한다.

## 수용 기준

- [ ] 34MB 관리자 PDF를 전송 완료한 뒤 Safari/PWA를 닫아도 보관함에 완성본이 생긴다. *(수동 테스트 필요, 미검증)*
- [x] 일반 사용자의 10MB 상한과 기존 생성 흐름은 변하지 않는다.
- [x] 서버 재시작 후 대기·진행 작업은 한 번만 재개된다(조건부 선점으로 검증).
- [x] 결과 저장 실패 시 MP3/DB 고아 객체를 정리하고 작업은 `error`가 된다.
- [x] 완료한 작업은 원본 파일·원문 텍스트를 보관하지 않는다(실패한 작업은 디버깅을 위해 남긴다 — 위 "저장 및 복구" 참고).

## 기술 메모

- `background_synthesis_jobs` 테이블 스키마는 `SUPABASE_SETUP.md` 2.5절에 있다.
- 결과 저장(`_store_background_audiobook`)은 Storage 업로드를 모두 마친 뒤에만 `audiobooks` 행을 만든다. 순서를 반대로 하면 업로드 중간 실패 시 파일 없는 행이 고아로 남는다.
- `storage.objects`는 service role만 사용하며, public RLS 정책을 만들지 않는다. `background_synthesis_jobs`도 동일하게 RLS만 켜고 정책은 두지 않는다.

## 검증

- 단위(`tests/test_background_jobs.py`): 동시 실행 제한(429)과 정상 큐잉, 로그인 필요, 실제 여유 디스크 부족 시 거절, 결과 저장 순서(고아 방지 및 롤백), 재시작 재개와 조건부 선점(중복 방지), source_text 없는 행 스킵, 문서 전체 재시도(첫 시도 성공/재시도 후 성공/전량 소진 후 error). 13개 테스트, 전부 mock 기반이라 실제 Storage/DB 없이 실행된다.
- 회귀 확인: 안전장치(조건부 선점) 코드를 일부러 제거해 대응 테스트가 실제로 실패하는 것을 확인한 뒤 원복 — 테스트가 형식적으로만 통과하는 게 아님을 검증했다.
- 수동(미완료): iOS Safari에서 34MB PDF 전송 완료 후 앱을 종료하고 보관함 확인.
