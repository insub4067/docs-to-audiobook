# TextAudio 종합 검토 보고서

작성일: 2026-08-07 · 대상 커밋: `.60`(`2026.08.07.60`)

이 문서는 코드·데이터베이스·프로덕션 로그를 직접 조사해서 쓴 것이다. 인상이
아니라 확인한 숫자를 근거로 삼았고, 확인하지 못한 것은 그렇다고 적었다.

---

## 0. 한 문단 요약

기술적으로는 **1인 개발 프로젝트치고 매우 잘 만들어져 있다.** 4,800줄 백엔드에
89% 테스트 커버리지, 회귀 테스트마다 "왜 이 코드가 이렇게 생겼는지"가 주석으로
남아 있고, 실패 사례가 문서로 축적돼 있다. 문제는 코드가 아니라 **쓰는 사람이
없다는 것**이다. 가입자 6명 중 실제로 무언가를 만들거나 들은 사람은 **2명**이고,
그중 하나는 개발자 본인이다. 지금 필요한 건 기능 추가가 아니라 "누가 왜 이걸
쓰는가"에 대한 답이다.

## 1. 프로젝트 개요

문서(PDF·텍스트·웹페이지·유튜브·구글 드라이브)를 TTS로 오디오북으로 바꿔 듣는
PWA. 여기에 관리자가 큐레이션하는 **경제 뉴스**와 **고전·경전 라이브러리**가
얹혀 있다.

| 구성 | 스택 |
| --- | --- |
| 백엔드 | FastAPI (Python 3.11), 라우트 17개 / 엔드포인트 58개 |
| 프론트 | Vue 3 SPA (컴포넌트 78개), Pinia, 런타임 의존성 3개뿐 |
| 저장소 | Supabase (Postgres + Storage), 클라이언트 IndexedDB |
| TTS | edge-tts / Google Cloud TTS (어댑터로 추상화) |
| 배포 | Fly.io 단일 머신(nrt), Docker |

| 규모 | 수치 |
| --- | --- |
| 백엔드 코드 | 4,837줄 |
| 프론트 코드 | 10,640줄 (+ CSS 4,484줄) |
| 테스트 | 40개 파일 6,970줄 / 백엔드 286 + 프론트 110 = **396개** |
| 백엔드 커버리지 | **89%** |
| 앱 번들 | 290KB (gzip 96KB) |

## 2. 프로그래밍 관점

### 2.1 강점

**아키텍처 규율이 실제로 지켜지고 있다.** View/State/Logic 3분할이 78개
컴포넌트 전반에 일관되게 적용돼 있고, 데이터 접근 계층(`indexedDb.ts`)처럼
UI 상태가 없는 곳은 의도적으로 분할하지 않는다는 판단까지 주석에 남아 있다.
규칙을 기계적으로 적용하지 않고 이유를 갖고 적용한 흔적이다.

**주석이 "무엇"이 아니라 "왜"를 적는다.** 이게 이 코드베이스의 가장 큰 자산이다.

> `⚠️ 이 라우트는 반드시 "/api/library/{audiobook_id}"보다 먼저 등록해야 한다.`
> `(실제로 그래서 이 엔드포인트는 추가된 이후 한 번도 동작한 적이 없었다.)`

이런 주석이 수십 개 있다. 6개월 뒤의 자신이나 다른 개발자가 같은 함정을 다시
밟지 않게 한다.

**테스트가 회귀를 실제로 잡는다.** 단순 커버리지 채우기가 아니라, 고친 코드를
되돌리면 해당 테스트만 깨지는지(뮤테이션) 확인한 흔적이 있다. 예: 장 경계 판정에
`activeIndex` 대신 직전 시각을 쓰는 이유가 테스트로 고정돼 있다.

**TTS 공급자 추상화가 제대로 됐다.** `TTSProvider` 어댑터 덕분에 edge-tts와
Google TTS를 음성 단위로 섞어 쓸 수 있고, 실제로 공급자를 갈아끼운 이력이 있다.

### 2.2 약점과 위험

#### (A) 조용한 실패가 반복되는 구조 — 가장 심각

오늘 하루에만 **같은 유형의 버그를 세 개** 찾았다.

| 버그 | 증상 | 원인 |
| --- | --- | --- |
| 재생 위치 저장 | `playback_history`가 **통째로 비어 있었음** | `INTEGER` 컬럼에 실수 전송 → 500 → 클라이언트가 무시 |
| `playback_started` | 대시보드 지표가 영원히 0 | 이벤트를 찍는 코드가 아예 없음 |
| `generation_completed` | 생성 성공률 3.7%로 표시 | 백그라운드 경로가 완료 이벤트를 안 탐 |

세 개 모두 **몇 주 동안 아무도 몰랐다.** 공통 원인은 "실패해도 사용자 경험이
안 망가지므로 조용히 무시한다"는 설계다. 재생은 계속되니까 위치 저장 실패를
삼키는 건 합리적이지만, **그 실패가 아무 데도 보고되지 않는 게 문제다.**

`gen_started 54 / gen_completed 2 / gen_failed 4` — 48건이 어디로 갔는지
설명되지 않는다. 이게 지표 버그인지 진짜 실패인지 지금도 확신할 수 없다.

**권고:** 클라이언트에서 삼킨 실패를 서버로 한 줄 보내는 최소 텔레메트리.
Sentry까지 갈 필요 없이 `POST /api/client-errors` 하나면 된다.

#### (B) 단일 머신 · 인메모리 상태

`fly.toml`에 정직하게 적혀 있다.

> 반드시 1대만 떠야 한다. `text_storage`와 `jobs`가 프로세스 인메모리라
> 머신이 2대면 업로드와 합성이 서로 다른 머신에 붙어 404가 난다.

수평 확장이 **구조적으로 불가능하다.** 사용자가 늘면 그날 바로 막힌다. 지금은
사용자가 2명이라 문제가 아니지만, "성장하면 그때 고치자"가 통하지 않는 종류의
제약이다 — 업로드→합성 흐름 전체를 다시 설계해야 하기 때문이다.

동시에 **CPU 1개(shared)** 위에서 TTS 합성이 돈다. 한 명이 대용량 문서를 넣으면
다른 사람의 변환이 굶는다. 실제로 코드 주석이 그 걱정을 하고 있다.

#### (C) "작품 하나 = MP3 하나"

라이브러리 작품의 장(章)은 파일이 아니라 **한 MP3 안의 타임스탬프**다. 덕분에
장 이동·장 반복은 싸게 구현됐지만, 다음이 구조적으로 막힌다.

- 장 단위 오프라인 다운로드
- 일부 장만 재생성(오타 수정 시 전체 재합성)
- 장별 스트리밍 최적화

12시간짜리 성경을 넣으면 단일 MP3가 수백 MB가 된다. **콘텐츠를 본격적으로
늘리는 순간 이 결정이 병목이 된다.**

#### (D) 품질 도구 부재

린터·포매터가 **하나도 없다.** ESLint, Prettier, ruff, black 모두 없다.
CI는 테스트와 배포만 한다. 지금은 코드 스타일이 일관되지만 그건 한 사람이
쓰기 때문이고, 두 번째 사람이 들어오는 순간 무너진다.

`style.css` 4,071줄 단일 파일도 같은 문제다. 컴포넌트는 잘 쪼개 놓고 스타일은
한 덩어리다.

#### (E) 보안 — 실질적 위험은 낮으나 오해의 소지

조사 결과:

- 모든 테이블에 RLS가 켜져 있다. ✅
- 그러나 `users`, `audiobooks`, `folders`, `playback_history`는 **`anon`에
  전체 CRUD 권한이 열려 있다.**
- RLS 정책은 `auth.uid() = user_id` 기반인데, 이 앱은 **Supabase Auth를 쓰지
  않고 자체 JWT를 쓴다.** 따라서 anon 키로 접근하면 `auth.uid()`가 NULL →
  정책이 모두 거부한다.

**결론: 지금은 새지 않는다.** 하지만 이건 "정책이 우연히 막아주는" 상태다.
정책을 하나만 잘못 고치면 `users` 테이블 전체가 열린다. 권한 자체를 회수하는
게 맞다(`content_jobs`, `library_saves`, `push_subscriptions`는 이미 그렇게
돼 있다 — 일관성만 맞추면 된다).

관리자 판별이 **이메일 문자열 비교(`ADMIN_EMAILS`)**인 것도 단순하지만, 이메일은
소셜 로그인 제공자가 바꿀 수 있는 값이다. 사용자 수가 적을 때는 문제없다.

#### (F) 데이터 정합성

`content_jobs` 도입 전, 등록이 실패하면 **아무 흔적도 남지 않았다.** 오늘
고쳤지만 같은 유형이 다른 곳에도 있을 수 있다. 특히 Storage 업로드와 DB insert가
트랜잭션으로 묶이지 않아, 중간에 실패하면 고아 파일이 남는다(일부 경로는
`storage.remove`로 보상하지만 전부는 아니다).

## 3. UI/UX 관점

### 3.1 강점

**모바일 우선이 립서비스가 아니다.** 44px 터치 영역, iOS 확대 방지를 위한 16px
입력 글꼴, safe-area 실측(상수 대신 `ResizeObserver`로 잰다), 세로 모드 잠금까지
챙겨져 있다. 웹앱인데 네이티브 앱처럼 느껴지는 이유다.

**읽기 경험이 이 앱의 핵심 자산이다.** 4가지 테마, 명조/고딕, 글자 크기·줄 간격,
문장 단위 하이라이트와 오디오 동기화. 오늘 측정한 본문 대비는 전 테마에서
**10.95:1 이상**(WCAG AAA 기준 7:1)이다.

**접근성이 평균 이상이다.** `aria-label`이 아이콘 버튼마다 붙어 있고,
`prefers-reduced-motion`과 `prefers-color-scheme`을 존중한다.

### 3.2 약점

#### (A) 첫 화면이 무엇을 하는 앱인지 말하지 않는다

홈에 들어가면 업로드 카드, 경제 뉴스, 최근 추가, 즐겨찾기가 동시에 보인다.
**처음 온 사람에게 "이걸로 뭘 하면 되는지"를 알려주는 장치가 없다.** 온보딩,
빈 상태 안내, 샘플 체험 유도가 전부 없다.

가입자 6명 중 4명이 아무것도 안 한 사실과 무관하지 않을 가능성이 높다.

#### (B) 기능 밀도가 발견성을 앞질렀다

"더보기" 시트 하나에 목차·이전 장·다음 장·문장 저장·저장한 문장·공유·읽기
설정이 들어 있다. 오늘만 4개를 추가했다. **자주 쓰는 것과 가끔 쓰는 것이 같은
깊이에 있다.**

장 이동은 경전 청취의 주된 이동 수단인데 2탭이 필요하다. 반면 10초 앞뒤 이동은
하단에 상시 노출돼 있다. 우선순위가 뒤바뀌어 있다.

#### (C) 콘텐츠 정체성이 세 갈래로 갈라진다

한 앱 안에 성격이 다른 셋이 공존한다.

| | 성격 | 소비 패턴 |
| --- | --- | --- |
| 내 문서 | 도구(utility) | 필요할 때만 |
| 경제 뉴스 | 소비형 피드 | 매일 짧게 |
| 라이브러리 | 장시간 콘텐츠 | 반복·정주행 |

세 개를 하나로 묶는 서사가 없다. 탭 이름도 "서재/서점"으로 은유가 섞여 있다
(서점인데 무료다).

#### (D) 실패 상태 노출이 얇다

TTS 실패, 네트워크 끊김, 저장 실패가 대부분 토스트 한 줄이거나 침묵이다.
"왜 안 됐는지"와 "어떻게 하면 되는지"가 없다.

## 4. 시장성 관점

### 4.1 실제 사용 데이터 (2026-08-07 기준)

| 지표 | 값 |
| --- | --- |
| 가입자 | 6명 |
| **실제로 무언가를 한 사용자** | **2명** |
| 주간 활성 사용자(WAU) | 2명 |
| 이벤트가 발생한 날 | 6일 |
| 생성된 개인 문서 | 9개 |
| 라이브러리 작품 | 8개 |
| 경제 뉴스 | 10건 |
| 라이브러리 "서재에 저장" | **0건** |
| 푸시 구독 | 3건 |
| 첫 가입 | 2026-07-29 (9일 전) |

**이 숫자를 정직하게 읽으면:** 아직 제품이 아니라 **잘 만들어진 프로토타입**이다.
가입자의 67%가 한 번도 쓰지 않았고, 큐레이션에 공을 들인 라이브러리를 서재에
저장한 사람이 한 명도 없다.

### 4.2 시장 구조

경쟁 상대가 층위별로 다르다.

| 층위 | 경쟁자 | 이 앱의 위치 |
| --- | --- | --- |
| OS 기본 | iOS "말하기 화면", 크롬 읽어주기 | 무료·기본 탑재. **가장 강력한 경쟁자** |
| 문서 TTS | Speechify, NaturalReader, Voice Dream | 유료, 고품질 음성, 브랜드 |
| 오디오북 | 밀리의서재, 윌라, Audible | 전문 성우, 라이선스 콘텐츠 |
| 경전·고전 | 각 종교단체 앱, 유튜브 낭독 채널 | 무료, 이미 커뮤니티 보유 |

**핵심 질문: 왜 iOS 기본 기능 대신 이걸 써야 하는가?**

현재 답이 될 수 있는 것:
- 문장 단위 하이라이트 + 오디오 동기화 (기본 기능에 없음)
- 오프라인 재생용 파일로 남음 (기본 기능은 그때그때 읽음)
- 폴더 정리, 이어 듣기, 진행률 (기본 기능에 없음)

이건 **실재하는 차별점**이다. 다만 지금 앱 어디에도 이 차별점이 설명돼 있지 않다.

### 4.3 라이브러리 전략에 대한 우려

경전·고전 큐레이션은 매력적이지만 세 가지 위험이 있다.

1. **저작권.** 원전이 만료돼도 **번역문은 별개다.** 코드에 이 원칙이 명시돼
   있고 `review`/`published` 분리도 잘 돼 있다. 다만 `library_rights`가 자유
   입력 문자열 하나라, 작품이 늘면 "이 판본 확인했던가?"를 추적할 수 없다.
2. **차별화 부재.** 무료 경전 낭독은 유튜브에 이미 많다.
3. **저장 0건.** 8개 작품에 대해 아무도 서재에 담지 않았다. 콘텐츠가 매력이
   없는 건지, 발견이 안 되는 건지, 저장 버튼이 안 보이는 건지 지금은 구분할
   수 없다.

### 4.4 비용 구조

| 항목 | 현재 |
| --- | --- |
| Fly.io | 1GB 머신 상시 가동(오늘 `suspend`로 전환) |
| Supabase | 무료 티어 추정 |
| Google TTS | 사용량 과금 — **사용자가 늘면 선형 증가** |

TTS는 사용자당 변동비다. 무료로 제공하면 **성장이 곧 적자**다. 수익 모델이
없는 상태에서 사용자가 늘면 그 자체가 위기가 된다.

**10. 수익 모델.** TTS가 변동비인 이상 무료 무제한은 지속 불가능하다.
월 N자 무료 + 초과 유료가 가장 단순한 형태다.
