# 서점 시리즈와 재생목록 설계

2026-08-18 · 구현 완료(`feature/library-series`)

오디세이처럼 긴 작품을 여러 "부"로 나눠 서점에 올리고, 부 하나를 틀면 작품
끝까지 이어 들리게 한다.

## 문제

서점 작품 하나는 `audiobooks` 행 하나이고 오디오 파일도 하나다. 오디세이를
24권으로 올리면 서점 화면에 서로 무관한 카드 24장이 깔려 나머지 작품이 전부
밀려난다. 반대로 한 편으로 합치면 몇 시간짜리 파일이 되어 원하는 대목으로
갈 수도, 어디까지 들었는지 알 수도 없다.

재생목록 기계 자체는 이미 있었다. `playlistNavigation.ts`가 "뉴스" 또는
"같은 폴더"를 큐로 삼아 앞뒤 이동·연속 재생·전체 반복을 처리한다. 없던 것은
**묶음이라는 단위**와 그것을 큐로 태우는 연결이다.

## 결정

### 서점의 "작품"은 `library_part_of`가 NULL인 행이다

`audiobooks`에 컬럼 세 개를 더했다. `library_part_of`, `library_part_number`,
`library_part_title`.

| 값 | 의미 |
|---|---|
| `part_of = NULL`, `part_number = NULL` | 단권 작품 |
| `part_of = NULL`, `part_number = 1` | 시리즈의 1부 = 작품 대표 행 |
| `part_of = <1부 id>`, `part_number = 2..N` | 2부 이후 |

목록 쿼리가 `where is_library and library_part_of is null`로 끝난다. 그룹핑
코드가 없고 인덱스가 처리한다. 기존 단권 작품은 세 컬럼이 전부 NULL이라
손대지 않아도 이전과 똑같이 동작한다.

**대안으로 검토한 것.** `library_works` 테이블을 새로 만드는 안(개념적으로
가장 정직하지만 `library_saves`의 FK를 갈아끼우고 프론트 타입과 테스트를
전부 손봐야 함)과, 시리즈만 새 테이블로 두는 안(목록·상세·저장·검색이 전부
"시리즈인가 단권인가"로 영구히 갈림)을 봤다. 자기 참조 컬럼이 두 안의 실질적
이점을 컬럼 두 개로 얻으면서 데이터 이관이 없다.

### 오디오북 id를 저장 시점이 아니라 큐잉 시점에 확정한다

이 설계의 핵심이다. 2부는 자기가 어느 작품에 속하는지 적어야 하는데 그 값이
1부의 id다. 저장할 때 `uuid4()`를 만들면 2부가 미리 알 방법이 없다.

`_expand_to_job_items`가 큐잉하면서 N개 uuid를 미리 뽑아 job metadata에 넣고,
`store_library_item`은 그 값이 있으면 그대로 쓴다. 얻은 것이 셋이다.

- 부들이 어떤 순서로 합성되든, 중간이 실패하든 관계가 어긋나지 않는다
- 실패한 부를 재시도하면 **같은 id로** 행이 되살아나 나머지 부에 그대로 붙는다.
  1부가 실패해 작품이 통째로 안 보이던 상태도 재시도 한 번으로 복구된다
- 같은 작업이 두 번 돌면 두 번째가 기본키 충돌로 막힌다. 무작위 uuid였다면
  같은 부의 오디오북이 조용히 두 개 생겼을 자리다

### `library_part_of`에 외래키를 걸지 않는다

자기 참조 FK에 `on delete cascade`가 더 안전해 보이지만 재시도 경로를
망가뜨린다. 5부만 재시도하면 그 작업은 단독으로 도는데, 그때 1부가 없으면
FK 위반으로 또 실패한다. 지금 서점에는 삭제 엔드포인트 자체가 없어 cascade가
막을 사고도 없다. 정합성은 위의 id 고정이 보장한다.

### 부분 성공을 정상 상태로 인정한다

| 상황 | 결과 | 복구 |
|---|---|---|
| 중간 부 실패 | 작품은 뜨고 부 번호에 구멍 | 재시도 → 같은 id로 메워짐 |
| 1부 실패 | 작품이 목록에 안 뜸, 나머지는 고아 | 1부 재시도 → 한 번에 연결 |
| 전부 실패 | 아무것도 안 뜸 | `content_jobs`에 원문 그대로 |

24개를 한 시간 합성하다 20번째에 끊겼을 때 처음부터 다시 하는 것이 더 나쁘다.

### 등록 상한은 작품이 아니라 부로 센다

`MAX_LIBRARY_PARTS_PER_REQUEST = 30`. 24권짜리 하나는 작품 수로는 1이지만
합성은 24번 돌아 공유 CPU를 그만큼 오래 문다. 세는 단위는 CPU를 무는 시간에
맞춰야 한다.

### 목록의 부 요약은 캐시하지 않고 매번 집계한다

카드에 "전 24부 · 약 5시간"을 띄우려면 부 정보가 필요한데, 작품마다 조회하면
N+1이다. 목록에 뜬 작품들의 부를 **한 번의 쿼리**로 받아 파이썬에서 합산한다.
1부 행에 미리 계산해 두는 방법도 있지만, 부가 하나씩 완성될 때마다 누적
UPDATE를 해야 하고 그 값이 어긋나면 고치기 번거롭다.

이 쿼리는 서명 URL을 만들지 않는다. 목록에서 부까지 서명하면 한 번에 수백 개를
서명하게 되는데 목록 화면에서는 재생하지 않아 쓰이지 않는다.

### 시리즈는 어느 부에서 시작했든 다음 부로 이어진다

뉴스와 의도적으로 다르게 했다. 뉴스는 "전체 듣기"로 시작했을 때만 다음
기사로 넘어간다(`isContinuous`). 시리즈에는 그 플래그가 없다 — 책의 다음 장이
이어지는 건 당연하고, 낱개 기사와 달리 부는 그 자체로 완결된 항목이 아니다.

### News_Logic과 합치지 않는다

`Library_Logic`의 큐 처리는 `News_Logic`과 구조가 거의 같다. 그래도 공용
모듈로 뽑지 않았다. 뉴스에는 백그라운드 자동재생 차단을 피하려고 다듬은
처리(동기 `onEnded`, 다음 항목 미리받기)가 들어 있고 매일 도는 기능이다.
라이브러리 재생이 실사용으로 검증된 뒤에 합치는 것이 낫다 — **후속 과제**.

## 함께 고친 것

**이어 듣기.** 작품 id는 곧 1부의 id다. 그대로 두면 3부까지 듣고 앱을 껐다 켠
사람이 1부로 돌아간다. 재생 위치는 `playback_history`가 `audiobook_id` 단위로
저장하므로 부마다 따로 남는다 — 기록이 있는 부 중 가장 뒤엣것에서 재개한다.

**서명 URL 만료.** 24부짜리는 다 듣는 데 몇 시간이 걸려 1시간짜리 URL이 도중에
죽는다. 다음 부를 미리 받을 때 만료가 가까우면 상세를 다시 받아 갱신한다.

**공유 버튼.** 상세의 "내 서재에 추가" 아래. Web Share API가 있으면 OS 공유
시트를, 없으면 클립보드 복사로 떨어진다. 시트를 그냥 닫아 나는 `AbortError`는
실패가 아니라 취소라 조용히 넘어간다.

## JSON 형식

기존 서점 등록 형식에 `parts`만 더했다. `parts`가 없으면 지금까지처럼 단권으로
처리하므로 예전 JSON은 그대로 동작한다.

```json
[{
  "title": "오디세이",
  "category": "고전문학",
  "description": "...",
  "edition": "", "translator": "", "source": "", "rights": "",
  "status": "review",
  "parts": [
    { "title": "제1권 · 아테나의 방문", "content": "..." },
    { "title": "제2권 · 텔레마코스의 출항", "content": "..." }
  ]
}]
```

`parts`의 배열 순서가 곧 재생 순서다. 번호를 따로 받지 않는 이유는, 받으면
빠진 번호와 중복 번호를 어떻게 다룰지 정해야 하는데 순서만으로 충분히
표현되기 때문이다.

부 하나는 4,000~8,000자가 적당하다. 한국어 TTS로 12~25분이고, 이보다 짧으면
재생목록만 길어진다.
