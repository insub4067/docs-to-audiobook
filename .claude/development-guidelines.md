# Development Guidelines

## 0. 에이전트 사용 규칙

1. **코드를 쓰기 전에** 이 문서를 읽고, 작업 대상 코드베이스의 기존 관례를 먼저 파악한다. 이 문서보다 **기존 코드베이스의 일관성이 우선**한다.
2. 코드를 쓴 뒤 §16 체크리스트로 자가 검증한다. 통과하지 못한 항목은 고치거나, 못 고쳤음을 명시한다.
3. 사용자의 명시적 지시가 이 문서와 충돌하면 사용자 지시가 우선한다. 충돌 사실만 한 줄로 알리고 진행한다.
4. **요청되지 않은 것을 만들지 않는다.** 추상화 계층, 설정 옵션, 확장 포인트, 유틸 함수를 "나중에 쓸 것 같아서" 추가하지 않는다.
5. 모르면 추측하지 않는다. 라이브러리 API·시그니처·동작은 실제로 확인하고, 확인이 불가능하면 그 사실을 밝힌다.

## 1. 핵심 철학 (한 문장)

> **코드는 쓰이는 시간보다 읽히는 시간이 압도적으로 길다. 우리가 싸우는 대상은 버그가 아니라 복잡도다.**

세 거장의 명제가 이 문서의 뼈대다.

- **Brooks** — 복잡도에는 문제 자체에서 오는 *본질적 복잡도*와 우리가 만들어낸 *우발적 복잡도*가 있다. 우리가 줄일 수 있는 건 후자뿐이고, 대부분의 고통은 후자에서 온다.
- **Ousterhout** — 소프트웨어 설계의 가장 큰 적은 복잡도이며, 복잡도는 한 번에 생기지 않고 **조금씩 누적된다.** 그래서 "이번 한 번쯤은"이 가장 위험하다.
- **Hickey** — *Simple(단순함)*과 *Easy(쉬움)*은 다르다. 단순함은 얽혀 있지 않은 상태이고, 쉬움은 지금 손에 익은 상태다. **당장 쉬운 선택이 나중의 복잡도를 만든다.**

파생 명제:
- 영리한 코드보다 지루한 코드가 낫다. 디버깅은 작성보다 어렵기 때문에, 최대한 영리하게 짜면 디버깅할 능력이 남지 않는다(Kernighan).
- 지금 30분을 아끼려고 만든 우발적 복잡도는 앞으로 모든 사람의 시간을 계속 뺏는다.

## 2. 복잡도 진단 (Ousterhout)

코드가 복잡한지는 취향이 아니라 **증상**으로 판정한다. 아래 셋 중 하나라도 보이면 복잡한 코드다.

| 증상 | 정의 | 판정 질문 |
|---|---|---|
| **변경 증폭** | 사소한 변경 하나에 여러 곳을 고쳐야 함 | 색상 하나 바꾸려면 몇 개 파일을 열어야 하나 |
| **인지 부하** | 무언가를 고치려면 알아야 할 것이 너무 많음 | 이 함수를 안전하게 쓰려면 사전 지식이 몇 개 필요한가 |
| **모르는 것을 모름** | 무엇을 고쳐야 하는지조차 알 수 없음 | 이 값을 바꿨을 때 어디가 깨질지 코드만 보고 알 수 있나 |

세 번째가 가장 나쁘다. 앞의 둘은 시간이 들지만, 세 번째는 **조용한 버그**를 만든다.

### 전술적 프로그래밍 vs 전략적 프로그래밍
- **전술적**: 지금 이 기능을 동작시키는 것이 목표. 빠르지만 복잡도가 누적된다.
- **전략적**: 좋은 구조를 유지하며 기능을 넣는 것이 목표. 매 작업에 약간(10~20%)을 더 쓴다.
- **기본은 전략적으로 간다.** 전술적으로 갈 때는 그 사실과 갚아야 할 부채를 명시적으로 기록한다.

## 3. 설계 원칙

### 3.1 모듈은 깊게 만든다 (Deep Module)
- 좋은 모듈 = **좁은 인터페이스 + 큰 기능**. 쓰는 사람이 알아야 할 것은 적고, 대신 해주는 일은 많다.
- 얕은 모듈(인터페이스가 기능만큼 복잡한 모듈)은 복잡도를 줄이지 않고 **위치만 옮긴다.** 껍데기만 씌운 래퍼 클래스, 한 줄짜리 위임 메서드가 대표적이다.
- 분해는 목적이 아니라 수단이다. "클래스를 잘게 쪼갤수록 좋다"는 명제는 **틀렸다.** 쪼갠 뒤 각 조각을 이해하기 위해 나머지 조각을 다 봐야 한다면 복잡도가 늘어난 것이다.
- 판정: 이 모듈을 쓰는 코드가 이 모듈의 **내부를 몰라도 되는가.**

### 3.2 정보 은닉 (Parnas)
- 모듈 분해의 기준은 "실행 순서"나 "레이어"가 아니라 **"무엇이 변할 것인가"**다. 변할 것으로 예상되는 결정마다 그것을 감싸는 모듈을 만든다.
- 각 모듈은 하나의 설계 결정을 감춘다. 그 결정이 바뀌면 **그 모듈만** 바뀌어야 한다.
- 안티: 내부 자료구조를 그대로 노출하는 게터, 내부 상태를 밖에서 조작하게 하는 세터, "일단 public"으로 열어둔 멤버.

### 3.3 결합도 — 나쁜 결합부터 없앤다

나쁜 순서대로:

| 결합 종류 | 예시 | 처방 |
|---|---|---|
| **전역/공유 가변 상태** | 싱글턴 가변 상태, 전역 변수 | 의존성으로 명시적 전달 |
| **구현 결합** | 남의 내부 구조·필드를 직접 참조 | 인터페이스·행위를 통해 접근 |
| **시간 결합** | `init()`을 먼저 불러야만 동작 | 생성자에서 완전한 객체를 만든다 |
| **제어 결합** | 불리언 플래그로 남의 분기를 조종 | 함수를 두 개로 분리 |
| **데이터 결합** | 필요한 값만 인자로 전달 | 목표 상태 |

- **디미터 법칙**: `a.b().c().d()`처럼 낯선 객체를 타고 들어가지 않는다. 이 체인은 중간 구조가 바뀔 때마다 깨진다.
- **Tell, Don't Ask**: 객체에서 데이터를 꺼내 판단하지 말고, 판단을 객체에게 맡긴다.
  ```
  ✗  if (order.getItems().size() > 0 && order.getStatus() == PAID) { ship(order) }
  ✓  if (order.isShippable()) { ship(order) }
  ```

### 3.4 응집도
- 하나의 모듈 안의 요소들은 **같은 이유로 함께 변해야** 한다.
- 판정 질문: 이 파일이 바뀌는 이유를 나열하면 몇 개인가. 두 개 이상이고 그 이유들이 서로 무관하면 분리한다.
- 반대로, 항상 같이 바뀌는 코드가 여러 파일에 흩어져 있으면 합친다. (산탄총 수술 스멜)

### 3.5 의존성 방향
- **정책이 세부사항에 의존하지 않게 한다.** 도메인 로직이 DB·HTTP·UI 프레임워크를 알면 안 된다. 반대로 그것들이 도메인을 알아야 한다.
- 의존성은 **더 안정적인 쪽**을 향한다. 자주 바뀌는 것이 덜 바뀌는 것에 의존한다.
- 경계에서 방향을 뒤집는다: 도메인이 인터페이스를 정의하고, 인프라가 그것을 구현한다.
- 순환 의존은 예외 없이 제거한다.

### 3.6 SOLID — 한 줄 요약과 실무 판정

| 원칙 | 의미 | 위반 신호 |
|---|---|---|
| **SRP** | 모듈이 바뀌는 이유는 하나 | "그리고"로 설명해야 하는 클래스 |
| **OCP** | 확장에는 열고 수정에는 닫는다 | 새 케이스마다 기존 `switch`를 고침 |
| **LSP** | 하위 타입은 상위 타입 자리에 그대로 들어간다 | 오버라이드가 예외를 던지거나 아무것도 안 함 |
| **ISP** | 안 쓰는 메서드에 의존하지 않는다 | 구현체가 절반을 빈 함수로 채움 |
| **DIP** | 추상에 의존한다 | 도메인 코드에 구체 라이브러리 타입이 등장 |

> 주의: SOLID는 목적이 아니라 **복잡도를 줄이기 위한 수단**이다. SOLID를 지키느라 얕은 모듈이 늘어나면 §3.1이 이긴다.

### 3.7 오류를 아예 존재할 수 없게 만든다
- 예외 상황을 처리하는 것보다, **예외 상황이 생길 수 없게 설계하는 것**이 낫다.
  - `null` 대신 빈 컬렉션 반환 → 호출부의 null 체크가 사라진다
  - 범위 초과 삭제를 오류로 만들지 말고, 자동으로 범위를 조정한다
- **불변식은 타입으로 강제한다.** 검증(validate)하지 말고 파싱(parse)한다. 검증된 값은 검증됐다는 사실이 타입에 남아야 한다.
  ```
  ✗  fun send(email: String)           // 호출부마다 유효성 검사 반복
  ✓  fun send(email: EmailAddress)     // 생성 시점에 한 번만 검증
  ```
- 표현할 수 없는 상태는 만들지 않는다. `isLoading`, `data`, `error` 세 필드로 8가지 조합을 만들지 말고, 하나의 상태 타입으로 4가지만 표현한다.

## 4. 단순 설계 4규칙 (Kent Beck) — 우선순위 순

충돌하면 **위에 있는 것이 이긴다.**

1. **모든 테스트를 통과한다** — 동작하지 않는 아름다움은 없다
2. **의도를 드러낸다** — 읽는 사람이 왜 이 코드가 있는지 알 수 있다
3. **중복이 없다** — 같은 *지식*이 두 곳에 있지 않다
4. **요소가 가장 적다** — 위 셋을 만족하는 선에서 가장 적은 클래스·메서드·개념

### 관련 규칙의 올바른 해석
- **DRY**는 코드 문자열의 중복이 아니라 **지식·의사결정의 중복**을 금지한다. 우연히 모양이 같은 두 코드를 합치면 결합도만 올라간다.
- **성급한 추상화는 중복보다 비싸다**(Metz). 세 번째 사례가 나올 때까지 기다린다(Rule of Three). 그때가 되어야 무엇이 진짜 공통인지 보인다.
- **YAGNI** — 지금 필요하지 않은 기능·유연성·설정을 만들지 않는다. 미래 요구사항 예측은 대부분 틀리고, 틀린 추상화는 지우기도 어렵다.
- **KISS** — 두 방법 중 고민되면 더 지루한 쪽을 고른다.

## 5. 이름 — 의도를 드러내는 첫 번째 수단

이름은 **가장 값싼 문서**다. 좋은 이름 하나가 주석 세 줄을 없앤다.

### 규칙
- 이름은 **무엇을/왜**를 말하고, **어떻게**는 감춘다. `sortedByPriceAsc` 대신 `cheapestFirst`.
- 도메인 용어를 그대로 쓴다(Evans, 유비쿼터스 언어). 기획서·회의·코드에서 같은 개념을 같은 단어로 부른다. 번역하지 않는다.
- 이름 길이는 **스코프에 비례**한다. 3줄짜리 루프 변수는 `i`로 충분하고, public API는 길어도 정확해야 한다.
- 불리언은 긍정형으로. `isDisabled == false`보다 `isEnabled`.
- 함수 이름은 동사구, 반환값이 있으면 무엇을 돌려주는지 드러낸다.
- **이름이 안 떠오르면 책임이 잘못 잡힌 것이다.** 이름을 억지로 짓지 말고 설계를 다시 본다.

### 금지
- 의미 없는 접미사: `Manager`, `Helper`, `Util`, `Processor`, `Handler`, `Data`, `Info`, `Service`(도메인 의미 없이 쓰는 경우)
- 축약: `usrCnt`, `tmpVal`, `procData`
- 타입을 이름에 넣기: `userList`(리스트가 셋으로 바뀌면 거짓말이 된다) → `users`
- 같은 개념을 다른 이름으로: `fetch/get/retrieve/load`를 섞어 쓰지 않는다. **하나를 골라 프로젝트 전체에서 그것만 쓴다.**

## 6. 함수와 클래스

- **함수는 한 가지 일만 한다.** "한 가지"의 판정: 함수 이름 아래 있는 모든 문장이 **같은 추상화 수준**인가 (SLAP).
  ```
  ✗  fun checkout() {
        validateCart(); 
        val tax = price * 0.1                 // 갑자기 계산 디테일
        db.execute("UPDATE ...")              // 갑자기 SQL
        notifyUser()
     }
  ✓  fun checkout() {
        validateCart()
        val total = calculateTotal()
        saveOrder(total)
        notifyUser()
     }
  ```
- **중첩 깊이 3을 넘기지 않는다.** 가드절(early return)로 예외 케이스를 먼저 걷어낸다.
- **인자는 3개 이하**를 목표로. 4개를 넘으면 함께 다니는 값들이 객체가 되어야 한다는 신호다(데이터 뭉치 스멜).
- **불리언 플래그 인자 금지.** `render(true)`는 호출부에서 아무 의미도 없다. 함수를 둘로 나눈다.
- **명령/질의 분리(CQS)**: 상태를 바꾸는 함수는 값을 반환하지 않고, 값을 반환하는 함수는 상태를 바꾸지 않는다. 어기려면 이름으로 반드시 드러낸다(`popNext`).
- 부수효과는 이름에 나타나야 한다. `getUser()`가 사용자를 생성한다면 그것은 거짓말이다.
- 참고 기준선(Metz): 클래스 100줄, 메서드 5줄, 인자 4개. **지키라는 규칙이 아니라, 어길 때 이유를 대라는 규칙이다.**

## 7. 주석과 문서

- 주석은 **코드가 표현할 수 없는 것**을 적는다.
  - ✅ 왜 이렇게 했는가, 어떤 대안을 왜 버렸는가
  - ✅ 계약: 사전조건, 사후조건, 불변식, 스레드 안전성, 성능 특성
  - ✅ 외부 세계의 사정: 버그 우회, 스펙 인용, 이슈 링크
  - ❌ 코드를 그대로 읽어주는 주석 (`// i를 1 증가시킨다`)
- **주석으로 나쁜 코드를 변명하지 않는다.** 주석이 길게 필요하면 대개 이름이나 구조가 잘못됐다.
- 인터페이스 주석은 **구현을 보지 않고도 쓸 수 있을 만큼**만 적는다. 구현 세부를 적으면 정보 은닉이 깨진다.
- **주석을 설계 도구로 쓴다.** 함수를 쓰기 전에 주석을 먼저 적어 보고, 그게 길고 복잡하다면 인터페이스가 잘못된 것이다.
- 오래된 주석은 **버그다.** 코드를 고치면 근처 주석을 함께 고친다.
- 커밋 메시지는 "무엇을"이 아니라 **"왜"**를 적는다. 무엇을 했는지는 diff가 말해준다.
- **주석 처리된 코드를 남기지 않는다.** 버전 관리 시스템이 그 일을 한다.

## 8. 상태와 부수효과

- **불변(immutable)을 기본값**으로 한다. 가변으로 만들 때만 이유가 필요하다.
- 가변 상태는 **범위를 최소화**한다. 지역 > 인스턴스 > 전역 순으로 좋다. 전역 가변 상태는 §3.3의 최악 결합이다.
- **순수한 계산과 부수효과를 분리한다.** 계산 로직은 I/O 없이 순수 함수로 두고, I/O는 바깥 껍질에 모은다. 이 구조는 테스트 가능성을 공짜로 준다.
- 동시성에서는 락을 잘 거는 것보다 **공유 가변 상태를 없애는 것**이 낫다.
- 시간·난수·현재 위치 같은 비결정적 입력은 직접 호출하지 말고 주입받는다. 테스트 가능해지고 의도도 드러난다.

---

## 9. 오류 처리

- **실패는 예외가 아니라 사례다.** 도메인에서 정상적으로 일어날 수 있는 실패(잔액 부족, 중복 가입)는 예외가 아니라 **반환 타입으로 표현**한다. 예외는 진짜 예외적인 상황에만.
- **빠르게, 시끄럽게 실패한다.** 잘못된 상태로 계속 진행하는 것이 즉시 죽는 것보다 나쁘다.
- **예외를 삼키지 않는다.** 빈 `catch` 블록은 금지. 처리할 수 없으면 위로 올린다.
- 로그만 찍고 계속 진행하는 것은 처리가 아니다. 무엇을 할지 결정할 수 없는 계층에서 잡지 않는다.
- 오류 메시지에는 **무슨 일이 일어났는지 + 무엇을 하면 되는지**를 담는다. 사용자에게 보이는 문구는 함께 쓰는 UX 문서의 규칙을 따른다.
- 오류에 맥락을 실어 전파한다. `FileNotFound`만 던지지 말고 어떤 파일인지, 무엇을 하려던 중이었는지 함께.
- 로그와 예외 메시지에 **개인정보·인증정보·토큰을 절대 넣지 않는다.**

---

## 10. 테스트

- **테스트는 실행 가능한 명세이자 문서다.** 테스트 이름만 읽어도 이 모듈이 무엇을 약속하는지 알 수 있어야 한다.
  ```
  ✗  fun testCase1()
  ✓  fun `잔액이 부족하면 송금이 거절된다`()
  ```
- 하나의 테스트는 하나의 개념을 검증한다. Given / When / Then 구조를 유지한다.
- **구현이 아니라 행위를 테스트한다.** 리팩터링으로 내부가 바뀌었을 때 깨지는 테스트는 나쁜 테스트다. 그런 테스트는 리팩터링을 막는다.
- **테스트하기 어렵다면 설계가 나쁘다는 신호다.** 테스트를 위해 억지 장치를 만들기 전에 설계를 의심한다.
- 커버리지 숫자 자체는 목표가 아니다. 중요한 것은 **깨지면 안 되는 것이 깨졌을 때 알려주는가.**
- 레거시 코드를 고칠 때는 먼저 현재 동작을 고정하는 특성화 테스트를 씌우고(Feathers), 이음새(seam)를 찾아 의존성을 끊은 뒤 손댄다.

---

## 11. 변경과 리팩터링

- **먼저 변경을 쉽게 만들고, 그다음 쉬운 변경을 하라**(Beck). 어려운 변경을 억지로 밀어붙이지 않는다.
- **정리와 기능 변경을 같은 커밋에 섞지 않는다.** 리뷰어가 무엇이 동작 변경이고 무엇이 이동인지 구분할 수 있어야 한다.
- 리팩터링은 **동작을 바꾸지 않는 것**이다. 동작을 보장할 테스트가 없다면 그것은 리팩터링이 아니라 도박이다.
- 보이스카우트 규칙: 손댄 파일은 처음보다 조금 더 깨끗하게 두고 나온다. 단, 무관한 대규모 정리를 끼워 넣지 않는다.
- 기술 부채는 **명시적으로 기록**한다. 조용한 부채가 가장 비싸다.

### 즉시 반응해야 할 코드 스멜 (Fowler)
| 스멜 | 신호 |
|---|---|
| 긴 함수 / 큰 클래스 | 스크롤 없이 전체가 안 보임 |
| 기능 편애 | 이 함수가 자기 클래스보다 남의 데이터를 더 씀 |
| 산탄총 수술 | 하나 바꾸려면 여러 파일을 조금씩 고쳐야 함 |
| 데이터 뭉치 | 같은 인자 3개가 항상 같이 다님 |
| 원시 타입 집착 | 금액·아이디·이메일이 전부 `String`, `Int` |
| 반복되는 switch/if 사슬 | 새 케이스마다 여러 곳을 고침 |
| 추측성 일반화 | 구현체가 하나뿐인 인터페이스, 쓰이지 않는 확장점 |
| 주석 과다 | 코드가 설명을 필요로 함 |

## 12. 일관성

**일관성은 개인 취향보다 항상 우선한다.** 일관된 코드베이스는 읽는 사람의 인지 부하를 직접 낮춘다.

- 새 코드는 **기존 코드의 관례를 따른다.** 더 나은 방식을 알더라도, 그 방식으로 전부 바꿀 것이 아니라면 도입하지 않는다.
- **같은 문제를 푸는 방식이 코드베이스에 둘 이상 존재하지 않게 한다.** 새 패턴을 도입하려면 기존 것을 대체하거나, 도입하지 않는다.
- 포매팅·임포트 순서·따옴표 같은 스타일은 도구(포매터·린터)가 결정한다. 사람이 논쟁하지 않고, 도구 설정을 저장소에 커밋한다.
- 디렉터리 구조, 파일 이름, 계층 이름, 에러 처리 방식, 로깅 형식, 테스트 위치는 프로젝트 전체에서 하나의 규칙을 따른다.
- **불변 규칙**: 이 문서와 기존 코드베이스가 충돌하면 **기존 코드베이스가 이긴다.** 개선은 별도 작업으로 제안한다.

## 13. 의도를 읽을 수 있는 시스템 만들기

코드는 "어떻게"를 말한다. **"무엇을, 왜"는 의도적으로 남겨야** 남는다.

### 13.1 구조가 도메인을 말하게 한다
- 디렉터리 구조를 열었을 때 보여야 하는 것은 **프레임워크가 아니라 이 시스템이 하는 일**이다.
  ```
  ✗  controllers/  services/  models/  utils/
  ✓  order/  payment/  delivery/  shared/
  ```
- 기술 계층은 도메인 안에서 나눈다. 도메인을 기술 계층 안에서 나누지 않는다.

### 13.2 왜를 기록한다 (ADR)
중요한 기술 결정마다 짧은 기록을 남긴다. 형식은 다섯 줄이면 충분하다.
```
제목 / 날짜 / 상태(제안·채택·폐기)
맥락:  어떤 상황과 제약이 있었나
결정:  무엇을 선택했나
대안:  무엇을 왜 버렸나
결과:  이 결정으로 무엇이 쉬워지고 무엇이 어려워지나
```
> 6개월 뒤 "왜 이렇게 했지?"에 답할 수 있는 유일한 수단이다. 코드는 결정의 *결과*만 남기고 *이유*는 지운다.

### 13.3 경계와 계약을 명시한다
- 모듈 진입점(공개 API)에 이 모듈이 **왜 존재하는지** 한 문단을 남긴다. 무엇을 하는지가 아니라 **어떤 문제를 대신 떠맡는지**를 쓴다.
- 외부 시스템과의 경계에는 계약을 문서화한다: 입력 형식, 실패 모드, 재시도 정책, 멱등성 여부, 타임아웃.
- 도메인 용어 사전을 저장소 안에 둔다. 용어가 흔들리면 코드도 흔들린다.

### 13.4 코드에 의도를 새기는 작은 습관
- 매직 넘버·매직 스트링에 이름을 준다. `if (status == 3)` → `if (status == Cancelled)`
- 조건식이 길면 이름 붙인 변수로 뽑는다. `val isEligibleForRefund = ...`
- 임시 변수 대신 의도를 담은 이름을 쓴다. `tmp`, `result2`, `data` 금지
- 도메인 규칙은 코드 여기저기 흩지 말고 한 곳에 모은다. 규칙을 찾을 수 있어야 바꿀 수 있다.

## 14. AI 에이전트 작업 규칙

코드를 생성·수정할 때 반드시 지킨다.

### 작업 전
1. 대상 파일과 그 주변 코드를 먼저 읽는다. 관례(이름, 구조, 에러 처리, 테스트 스타일)를 파악한다.
2. 이 변경의 의도를 **한 문장**으로 쓴다. 못 쓰면 요구사항을 더 물어본다.
3. 이미 존재하는 함수·타입·유틸을 다시 만들지 않는다. 검색해서 확인한다.

### 작업 중
4. **최소 변경.** 파일 전체를 재작성하지 않고, 필요한 부분만 고친다. 무관한 포매팅 변경을 섞지 않는다.
5. 요청되지 않은 기능·설정 옵션·추상화 계층·확장 포인트를 만들지 않는다.
6. 구현체가 하나뿐인 인터페이스를 만들지 않는다. 두 번째가 나타날 때 만든다.
7. 라이브러리 API·시그니처·버전별 동작은 확인하고 쓴다. 확실하지 않으면 그 사실을 명시한다.
8. 에러를 삼키지 않는다. `catch {}`, `except: pass`, `_ = try?` 를 남기지 않는다.
9. 비밀값(키·토큰·비밀번호)을 하드코딩하지 않고, 로그·에러 메시지에 개인정보를 남기지 않는다.
10. 성능 최적화는 **측정한 뒤에** 한다. 근거 없는 사전 최적화로 가독성을 팔지 않는다.

### 작업 후
11. 죽은 코드, 주석 처리된 코드, 디버그 출력, 임시 TODO를 남기지 않는다. 남겨야 한다면 이유와 함께 명시적으로 남긴다.
12. 변경한 동작에 대응하는 테스트를 함께 제시한다. 테스트를 쓸 수 없는 상황이면 이유를 밝힌다.
13. §16 체크리스트로 자가 검증한다.
14. 사용자에게 보고할 때 **무엇을 왜 그렇게 했는지, 어떤 선택지를 버렸는지**를 짧게 덧붙인다. 코드만 던지지 않는다.

## 15. 안티패턴 (발견 즉시 수정)

- 껍데기만 씌운 래퍼 클래스, 한 줄 위임 메서드 (얕은 모듈)
- 구현체가 하나뿐인 인터페이스, 쓰이지 않는 확장 포인트
- 전역 가변 상태, 가변 싱글턴
- 불리언 플래그로 동작을 바꾸는 함수
- `a.b().c().d()` 형태의 긴 접근 체인
- 매직 넘버·매직 스트링
- 4단계 이상 중첩된 조건문
- 인자 5개 이상의 함수
- `Manager`, `Helper`, `Util`, `Data`, `Info` 로 끝나는 타입 이름
- 빈 `catch`, 예외를 로그만 찍고 넘어가는 코드
- 우연히 비슷하다는 이유로 합쳐진 두 로직
- 같은 개념에 대한 서로 다른 이름 (`fetch`/`get`/`load` 혼용)
- 코드를 그대로 읽어주는 주석, 오래되어 거짓이 된 주석
- 주석 처리된 채 남아 있는 코드
- 구현 세부에 결합되어 리팩터링마다 깨지는 테스트
- 정리와 기능 변경이 섞인 커밋

## 16. 자가 검증 체크리스트

**복잡도**
- [ ] 이 변경으로 다른 곳을 함께 고쳐야 하지 않는가 (변경 증폭)
- [ ] 이 코드를 쓰려는 사람이 알아야 할 사전 지식이 최소인가 (인지 부하)
- [ ] 이 값을 바꿨을 때 무엇이 영향받는지 코드만 보고 알 수 있는가

**설계**
- [ ] 각 모듈의 인터페이스가 기능에 비해 좁은가
- [ ] 이 파일이 바뀌는 이유가 하나인가
- [ ] 도메인 로직이 프레임워크·DB·UI를 모르는가
- [ ] 순환 의존이 없는가
- [ ] 전역 가변 상태와 시간 결합이 없는가

**단순함**
- [ ] 요청되지 않은 추상화·옵션·확장점을 만들지 않았는가
- [ ] 중복된 것이 코드 모양이 아니라 실제로 같은 지식인가
- [ ] 더 지루하고 짧은 방법이 남아 있지 않은가

**의도**
- [ ] 모든 이름이 무엇을·왜를 말하는가
- [ ] 매직 넘버·매직 스트링이 없는가
- [ ] 이 코드가 왜 존재하는지 코드나 주석이나 커밋에서 알 수 있는가
- [ ] 중요한 기술 결정을 기록했는가

**함수·오류**
- [ ] 함수 안의 문장들이 같은 추상화 수준인가
- [ ] 중첩이 3단계를 넘지 않는가
- [ ] 삼켜진 예외가 없는가
- [ ] 도메인 실패가 예외가 아니라 값으로 표현되는가

**일관성**
- [ ] 기존 코드베이스의 관례를 따랐는가
- [ ] 같은 문제를 푸는 방식이 하나인가

**안전·완결성**
- [ ] 비밀값 하드코딩, 로그의 개인정보 노출이 없는가
- [ ] 죽은 코드·주석 처리된 코드·디버그 출력이 없는가
- [ ] 동작을 검증하는 테스트가 있는가

## 18. 함께 쓰는 문서와의 관계

- `apple-design-principles.md` / `toss-design-principles.md` — **무엇을 만들 것인가**(UI·UX·기획)
- 이 문서 — **그것을 어떻게 지을 것인가**(코드·구조)

충돌 지점 해소:
- 사용자에게 보이는 문구·상태(로딩/빈 상태/오류) 정의는 디자인 문서가 결정하고, 그 상태를 코드에서 어떻게 표현할지는 이 문서 §3.7이 결정한다.
- 공통 상위 규칙: **사용자에게 안전하고 명확한 것 > 코드가 아름다운 것.**
