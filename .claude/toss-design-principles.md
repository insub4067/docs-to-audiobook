# Toss Design Principles

## 0. 에이전트 사용 규칙

이 문서는 **네가 만드는 화면, 문구, 플로우, 코드가 "토스가 만들었을 법한 결과물"인지 판정하는 기준**이다.

1. 작업 전 전체를 읽고, 산출물 완성 후 §12 체크리스트로 자가 검증한다.
2. 사용자의 명시적 요구가 이 문서와 충돌하면 사용자 요구가 우선한다. 충돌 사실만 한 줄로 알리고 진행한다.
3. **모든 문구는 §7 라이팅 규칙을 예외 없이 적용한다.** 문구는 나중에 다듬는 대상이 아니라 설계의 일부다.
4. 화면을 그리기 전에 "이 화면이 사용자에게 던지는 질문 하나"를 먼저 문장으로 쓴다. 그 문장이 안 나오면 화면 구조가 잘못된 것이다.

---

## 1. 핵심 철학 (한 문장)

> **Simplicity — 사용자가 따로 배우거나 알아야 할 것 없이, 설명 없이 본능적으로 이해되는 상태.**

여기서 단순함은 "요소가 적은 것"이 아니다. **사용자가 머리를 쓸 일이 적은 것**이다.
화면에 요소가 5개여도 사용자가 고민하면 복잡한 것이고, 정보가 많아도 판단이 즉시 서면 단순한 것이다.

핵심 명제:
- **디자이너가 쉬운 길을 택하면 사용자가 어려운 길을 걷는다.** 복잡함은 만드는 쪽이 감당한다.
- 단순함은 UI만의 문제가 아니다. **정책이 복잡하면 어떤 UI로도 구제되지 않는다.**
- 원칙은 취향이 아니라 검증된 승리 전략이다. "제 생각엔 이게 예뻐서"는 근거가 아니다.

## 2. 제품 전략 3원칙

기획·스펙 단계에서 적용한다.

### 2.1 Casual Concept — 개념을 사용자 언어로 번역한다
- 전문 용어(금융·법률·기술)를 사용자가 이해해야 하는 부담을 제품에 지우지 않는다.
- 도메인 용어를 그대로 노출하는 대신, 사용자가 이미 아는 개념으로 바꾼다.
  - `예: 잔여 한도 조회 → 얼마나 더 쓸 수 있는지 보기`
  - `예: 인증서 갱신 → 다시 로그인하기`
- 용어를 바꿀 수 없다면(법적 표기 등) 옆에 사용자 언어의 설명을 함께 둔다.

### 2.2 Minimum Features — 없으면 목표를 달성할 수 없는 기능만 넣는다
- 기능 추가는 **목표 달성을 위한 최후의 수단**이다. 먼저 기존 흐름 개선을 시도한다.
- 기능이 늘어날수록 제품은 어려워지고 개선 속도는 느려진다. 이 비용을 스펙 논의에 명시한다.
- 판정 질문: "이 기능을 빼면 사용자가 목표를 **절대** 달성할 수 없는가?" 아니면 뺀다.

### 2.3 Less Policy — 단순한 제품은 단순한 정책에서 나온다
- 예외 조건, 대상자 조건, 기간 조건이 늘어날수록 화면은 반드시 복잡해진다.
- **UI로 정책 복잡도를 감추려 하지 않는다.** 정책 자체를 줄이자고 제안한다.
- 사용자가 서비스를 쓰기 위해 "알아야 하는 것"의 개수를 세어보고, 그 수를 줄이는 방향으로 설계한다.

## 3. UX 8원칙 (화면 설계의 핵심)

### 3.1 One Thing per Page — 한 화면, 한 메시지
- 하나의 화면은 하나의 질문 또는 하나의 메시지만 전달한다.
- 긴 폼은 한 화면에 몰지 말고 단계로 쪼갠다. 각 단계는 대답 하나만 받는다.
- 같은 질문에 속하는 요소는 한 화면에 함께 둬도 된다 (예: 통신사 선택 + 번호 입력 = "전화번호가 뭐예요?" 하나의 질문).
- 판정: 화면 제목을 한 문장으로 못 쓰면 화면을 쪼개야 한다.

### 3.2 Tap & Scroll — 핵심 플로우는 탭과 스크롤만으로
- 주 흐름에 드래그, 롱프레스, 복잡한 제스처, 여러 손가락 조작을 넣지 않는다.
- 텍스트 입력은 최소화한다. 선택지로 바꿀 수 있으면 선택지로 바꾼다.
- 키보드가 필요하면 화면 진입 시 자동으로 올리고, 키패드 종류(숫자/이메일)를 정확히 지정한다.

### 3.3 Easy to Answer — 모든 질문은 3초 안에 답할 수 있어야 한다
- 사용자가 기억을 더듬거나 다른 앱을 열어야 하는 질문은 잘못된 질문이다.
- 알아낼 수 있는 정보는 시스템이 알아서 채운다. 사용자에게 묻지 않는다.
- 답하기 어려운 질문은 **더 쉬운 질문으로 분해**한다.
  - `나쁨: 어떤 방식으로 신청할까요? (직접 신청 / 상담 신청)`
  - `좋음: 서류를 갖고 있나요? (네 / 아니요)` → 답에 따라 경로를 나눈다.
- 선택지는 서로 배타적이고, 각 선택 후 무슨 일이 생기는지 예측 가능해야 한다.

### 3.4 Value First, Cost Later — 가치를 먼저, 비용은 나중에
- 정보 입력, 인증, 권한 허용, 가입은 **사용자가 가치를 확인한 뒤**에 요청한다.
- 진입 즉시 로그인 벽을 세우지 않는다. 볼 수 있는 것을 먼저 보여준다.
- 권한 요청은 그 권한이 실제로 필요해지는 순간, 왜 필요한지와 함께 띄운다.

### 3.5 No Ads Patterns — 광고가 아니라 기능으로 소구한다
- 배너 광고 스타일, 과장된 카피, 강조 남발을 쓰지 않는다.
- 혜택은 기능의 일부로 자연스럽게 배치한다. 광고처럼 보이면 사용자는 오히려 무시한다.
- 느낌표, 화려한 그라데이션, 반짝임 효과로 주목을 끌지 않는다.

### 3.6 Context-based — 사용자의 맥락 위에서 흐름을 만든다
- 사용자가 어디서 왔고, 무엇을 하려다 여기 왔는지에 따라 화면이 달라져야 한다.
- 맥락 없이 연결된 화면은 이탈을 만든다. 화면 사이의 인과가 문장으로 설명돼야 한다.
- 개인화된 정보(이미 아는 이름·계좌·상태)를 활용해 질문 수를 줄인다.

### 3.7 No More Loading — 사용자를 기다리게 하지 않는다
- 속도는 UX의 일부다. 기다림을 줄이기 위해 **정책·플로우·기술 전부를 동원한다.**
- 구체적 수단: 사전 로딩(prefetch), 낙관적 업데이트(optimistic UI), 스켈레톤, 캐시, 응답 분할 렌더링.
- 스피너는 최후의 수단이다. 스피너를 넣기 전에 "기다림 자체를 없앨 방법"을 먼저 검토한다.
- 실제로 기다릴 필요가 없는데 로딩 애니메이션을 보여주지 않는다. 사용자가 상황을 오해한다.

### 3.8 Sleek Experience — 의식되지 않을 만큼 매끄럽게
- 시선 이동과 손가락 동선에 어색함이 없어야 한다. 다음 탭할 곳이 손가락 근처에 있는가.
- 화면 전환, 포커스 이동, 키보드 등장이 끊기지 않고 이어진다.
- 완료 후 다음 행동이 자연스럽게 이어진다. 사용자를 빈 화면에 두고 끝내지 않는다.

## 4. 화면 구성 패턴

| 요소 | 규칙 |
|---|---|
| 화면 제목 | 큰 타이포로 상단. 사용자에게 던지는 질문 또는 이 화면의 결론을 그대로 문장으로 |
| 본문 | 여백을 넉넉히. 정보 밀도보다 스캔 가능성 우선 |
| 주요 CTA | 하단 고정, 화면당 1개, 라벨은 결과를 예측할 수 있는 동사형 |
| 보조 액션 | 텍스트 버튼 등 시각적 무게를 명확히 낮춰 배치 |
| 단계 표시 | 여러 단계 플로우는 진행 상황을 알 수 있게 |
| 바텀시트 | 짧은 선택·확인용. 진입 직후나 뒤로 가기 시점에 띄우지 않음 |
| 리스트 | 각 행이 무엇인지 한 줄로 읽히게. 부가 정보는 시각적 후순위 |
| 빈 상태 | 왜 비어 있는지 + 다음에 뭘 하면 되는지 |
| 오류 | 무슨 일이 생겼는지 + 사용자가 할 수 있는 행동 |

## 5. 다크패턴 금지 (예외 없음)

아래는 즉시 반려 대상이다.

1. **진입 직후 전면을 가로막는 바텀시트/팝업** — 광고성, 알림 동의 요청 포함
2. **뒤로 가기를 눌렀을 때 이탈을 막으려고 띄우는 바텀시트**
3. **빠져나갈 선택지가 없는 구조** — 유도된 CTA 외에 다른 선택이 불가능한 화면
4. **예상하지 못한 순간의 전면 광고** — 사용자가 다른 행동을 기대한 지점에서의 광고 노출
5. **눌렀을 때 무슨 일이 생길지 알 수 없는 CTA** — 화면 설명을 그대로 반복하는 모호한 버튼 라벨

추가 금지:
- 애원·호소·죄책감을 자극하는 표현과 그래픽
- 거절 버튼을 시각적으로 숨기거나 약하게 만드는 처리
- 가짜 긴급성(허위 카운트다운, 없는 재고 압박)

## 6. 그래픽·비주얼 규칙

- 그래픽은 **장식이 아니라 이해를 돕는 장치**다. 맥락에 맞지 않으면 넣지 않는다.
- **한 화면에 핵심 그래픽 하나.** 비슷한 크기의 그래픽이 여러 개면 시선이 분산된다.
- 스타일은 단순하고 명료하고 깨끗한 디지털 톤. 손그림풍, 서정적 화풍, 만화적 표현은 쓰지 않는다.
- 의미 없는 파티클, 과한 그라데이션, 반짝임 이펙트를 쓰지 않는다.
- 정보 밀도에 맞는 크기: 단순한 그래픽은 작게, 디테일이 많으면 충분히 크게.
- 그래픽이 핵심 정보를 밀어내 불필요한 스크롤을 만들지 않게 한다.
- **라이트/다크 모드 양쪽에서 모두 잘 보여야 한다.** 중간 명도를 쓴다.
- 아이콘은 화면에서 24~40px 범위, 한 번에 하나만 사용한다.
- 상황과 다른 기호를 쓰지 않는다 (오류가 아닌데 경고 아이콘, 기다림이 없는데 로딩 애니메이션).

## 7. UX 라이팅 규칙 (한국어)

**모든 문구에 예외 없이 적용한다.**

### 7.1 해요체
- 제품 안의 모든 문구는 해요체로 쓴다. 상황과 맥락을 불문하고 일관되게.
- `송금이 완료되었습니다 → 송금했어요`

### 7.2 능동형
- 수동형 대신 능동형을 기본으로 한다.
- `됐어요 → 했어요`
- `~었/였` 같은 과거 표지는 가능하면 덜어낸다.
- `변경되었어요 → 바꿨어요`

### 7.3 긍정형
- 부정 표현을 줄이고 할 수 있는 것을 먼저 말한다.
- `쿠폰이 없어요 → 쿠폰을 받으면 쓸 수 있어요`
- 서비스 전체는 쓸 수 있는데 특정 혜택만 못 받는 상황이면 **반드시 긍정형**으로 쓴다. 사용자는 문장을 훑어 읽기 때문에 제품 전체를 못 쓴다고 오해한다.

### 7.4 캐주얼한 경어
- 과도한 경어(`~시겠어요?`, `~께`)를 쓰지 않는다.
- `계시다 → 있다`, `여쭈다 → 확인하다/묻다`, `께 → 에게`, 동사의 `~시` 제거
- `~시`를 뺐을 때 어색하면, **알고 싶은 정보를 주어로 삼아 문장을 새로 쓴다.**
  - `이름이 어떻게 되세요? → 이름이 뭐예요?`

### 7.5 명사 나열 금지
- `{명사}+{명사}` 형태의 한자어 덩어리를 풀어서 동사형으로 쓴다.
- `본인 확인 실패 → 본인 확인을 못 했어요`
- 풀어쓰기 어려우면 `{명사}가 {명사}해서` 형태로만 바꿔도 훨씬 부드러워진다.

### 7.6 고정 규칙
- 다이얼로그 왼쪽 버튼은 **"닫기"**로 통일한다. "취소"는 사용자가 진행 중인 작업이 취소된다고 오해할 수 있어 쓰지 않는다.
- `되어요`는 모두 `돼요`로 쓴다. (좁은 모바일 화면 고려)
- 버튼 라벨은 누른 뒤 무슨 일이 생기는지 알 수 있는 동사형으로.
- 불필요한 단어(문장에서 빼도 의미가 그대로인 말)는 전부 제거한다.

### 7.7 예외 규칙 (아래 상황에서는 규칙을 벗어나도 된다)

**수동형을 써도 되는 경우**
- 서비스 종료·기간 만료: 종료되는 대상을 주어로 강조하고 뉘앙스를 정확히 전달할 때
  (단, 주기적으로 반복 종료되는 제품에는 "종료돼요"를 쓰지 않는다)
- 사용자 행동의 결과로 생기는 영향을 알릴 때 (연체, 해지, 적용 등) — 인과관계가 명확해진다
- 정보 수집 안내처럼 민감한 상황에서 사용자를 안심시킬 때

**경어를 써도 되는 경우**
- 사용자의 맥락을 활용해 물어봐서 당황을 줄일 때 (`~셨나요?`)
- 토스 쪽에 정보가 없어 사용자가 직접 판단해야 할 때
- 설문처럼 사용자의 선의를 기대해야 할 때

**부정형을 써도 되는 경우**
- 정책상 서비스를 쓸 수 없을 때 (반드시 이유를 함께 안내)
- 일부 기능만 쓸 수 없을 때 (무엇을 못 쓰는지 명확히)
- 사용자 선택의 결과를 분명히 알려야 할 때
- 민감한 상황에서 안심시켜야 할 때 (`~하지 않아요`)

## 8. 기술 방향성

- **속도가 곧 UX다.** 응답 시간을 기능 요구사항으로 다룬다. "빠르게"가 아니라 목표 수치로 명시한다.
- 낙관적 업데이트를 기본 전략으로 검토한다. 서버 응답을 기다리지 말고 UI를 먼저 반영하고, 실패 시 되돌린다.
- 다음 화면에서 쓸 데이터를 미리 가져온다. 화면 전환 시점에 요청을 시작하지 않는다.
- 로딩은 **스켈레톤 + 부분 렌더링**. 전체 화면 스피너는 마지막 선택지다.
- 단순한 경험일수록 뒤에서 감당할 일이 많다. **보안과 편의성이 상충한다는 전제를 받아들이지 않는다.** 사용자 단계를 늘리지 않으면서 안전하게 만들 방법을 먼저 찾는다.
- 화면 명세에는 로딩 / 빈 상태 / 오류 / 권한 거부 4가지 상태가 반드시 포함된다.
- 접근성: 스크린리더 레이블, 대비, 터치 타겟, 다이내믹 폰트 크기를 출시 조건으로 다룬다.
- 라이트/다크 모드를 동시에 설계한다.
- 판단이 갈리는 지점은 실험으로 검증한다. 취향 논쟁 대신 지표를 본다. 단, 지표가 나빠도 사용자 신뢰를 해치는 패턴은 채택하지 않는다.

## 9. 안티패턴 (발견 즉시 수정)

- 한 화면에 여러 질문을 몰아넣은 긴 폼
- 사용자가 답하려면 다른 앱이나 서류를 확인해야 하는 질문
- 가치를 보여주기 전에 요구하는 로그인·인증·권한
- 진입 직후 또는 뒤로 가기 시점의 바텀시트
- "확인" "다음" 같은 결과를 예측할 수 없는 모호한 CTA
- 도메인 전문 용어의 무번역 노출
- 필요 없는 로딩 애니메이션
- 화면당 동등한 무게의 CTA 2개 이상
- 해요체가 아닌 문구, 수동형·부정형 남용
- 애원조·과장 카피, 배너 광고형 컴포넌트
- 정책 복잡도를 안내 문구로 덮으려는 시도
- 그래픽 여러 개를 비슷한 크기로 나열

## 10. 판정 예시

```
❌  제목: 본인인증 미완료 안내
    본문: 본인인증이 완료되지 않아 서비스 이용이 제한됩니다.
    버튼: 확인

✅  제목: 본인 확인을 안 했어요
    본문: 본인 확인을 하면 바로 쓸 수 있어요.
    버튼: 본인 확인하기
```

- 해요체 적용 / 명사 나열 해체 / 부정형을 긍정형으로 전환 / CTA가 다음 행동을 명시

```
❌  질문: 어떤 방식으로 청구하시겠어요?  [직접 청구] [상담 신청]
✅  질문: 서류를 갖고 있나요?           [네] [아니요]
```

- Easy to Answer: 사용자가 3초 안에 답할 수 있는 질문으로 분해 후 경로 분기

## 11. Apple 문서와 함께 쓸 때

두 문서를 동시에 참조하는 경우 충돌 지점의 해소 기준:

| 충돌 지점 | 해소 |
|---|---|
| 정보 밀도 | 토스 기준(여백 넉넉히, 한 화면 한 메시지)을 따른다 |
| 컴포넌트·제스처·내비게이션 | Apple 기준(시스템 표준)을 따른다. 플랫폼 관례를 깨지 않는다 |
| 문구·톤 | 한국어 서비스면 토스 기준을 따른다 |
| 접근성·터치 타겟·대비 | Apple 기준 수치를 하한선으로 삼는다 |
| 시각 스타일 | 대상 플랫폼이 iOS면 Apple, 크로스플랫폼/웹뷰면 토스 |

공통 상위 규칙: **접근성 > 명료성 > 플랫폼 일관성 > 브랜드 표현**

## 12. 산출물 자가 검증 체크리스트

**단순함**
- [ ] 이 화면의 질문/메시지를 한 문장으로 쓸 수 있는가
- [ ] 사용자가 알아야 할 것을 더 줄일 수 있는가
- [ ] 뺄 수 있는 기능·정책·요소가 남아 있지 않은가

**흐름**
- [ ] 핵심 플로우가 탭과 스크롤만으로 완주되는가
- [ ] 모든 질문에 3초 안에 답할 수 있는가
- [ ] 시스템이 알아낼 수 있는 정보를 사용자에게 묻고 있지 않은가
- [ ] 가치를 보여주기 전에 비용(입력·인증·권한)을 요구하지 않는가
- [ ] 이전 화면과의 맥락이 문장으로 설명되는가

**속도**
- [ ] 기다림을 없앨 방법을 먼저 검토했는가
- [ ] 스켈레톤/프리페치/낙관적 업데이트를 적용했는가
- [ ] 필요 없는 로딩 표시가 없는가

**문구**
- [ ] 전부 해요체인가
- [ ] 능동형·긍정형인가 (예외 규칙에 해당하지 않는 한)
- [ ] 과도한 경어와 명사 나열이 없는가
- [ ] 다이얼로그 왼쪽 버튼이 "닫기"인가
- [ ] CTA만 보고 다음에 무슨 일이 생길지 알 수 있는가
- [ ] 전문 용어를 사용자 언어로 바꿨는가

**신뢰**
- [ ] §5 다크패턴 5가지 중 해당되는 것이 하나도 없는가
- [ ] 사용자가 언제든 빠져나갈 수 있는가
- [ ] 과장·애원·가짜 긴급성이 없는가

**완결성**
- [ ] 로딩 / 빈 상태 / 오류 / 권한 거부가 모두 정의되었는가
- [ ] 라이트·다크 모드 양쪽에서 확인했는가
- [ ] 접근성(레이블·대비·터치 영역)이 확보되었는가
