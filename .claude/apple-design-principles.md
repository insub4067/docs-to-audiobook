# Apple Design Principles

## 0. 에이전트 사용 규칙

이 문서는 **네가 만드는 화면, 컴포넌트, 코드, 기획안이 "애플이 만들었을 법한 결과물"인지 판정하는 기준**이다.

1. 작업 시작 전에 이 문서 전체를 읽고, 산출물을 만든 뒤 §11 체크리스트로 자가 검증한다.
2. 이 문서와 사용자의 명시적 요구가 충돌하면 **사용자 요구가 우선**한다. 단, 충돌 사실과 이 문서가 권하는 대안을 한 줄로 알린 뒤 진행한다.
3. 근거 없이 "예쁘게" 만들지 않는다. 모든 시각적 결정은 §1~§3의 원칙 중 하나로 설명 가능해야 한다.
4. 수치·API·컴포넌트 이름은 추측하지 말고 실제 SDK 버전 기준으로 확인한다. 확인 불가하면 시스템 기본값을 쓴다.

## 1. 핵심 철학 (한 문장)

> **인터페이스는 사라지고, 사용자의 콘텐츠와 목적만 남아야 한다.**

애플의 디자인은 "무엇을 더할까"가 아니라 **"무엇을 없애도 되는가"**의 축적이다.
UI가 눈에 띈다는 것은 대개 실패 신호다. 사용자가 UI를 의식하지 않고 자기 일에 몰입할 때 성공이다.

파생 명제:
- 기본값(default)이 곧 제품이다. 설정으로 해결하려 들지 말고 기본값을 옳게 만든다.
- 옵션을 늘리는 것은 결정을 사용자에게 떠넘기는 것이다.
- 완성도는 기능 개수가 아니라 마지막 5%의 디테일에서 결정된다.

## 2. 현행 3대 원칙 (iOS 26 이후, Liquid Glass 시대)

애플이 WWDC25에서 새 디자인 시스템의 구현 원칙으로 제시한 3가지다. **화면 설계 시 이 순서로 판단한다.**

### 2.1 Hierarchy (위계)
- 컨트롤·내비게이션은 콘텐츠 **위에 떠 있는 별도의 기능 레이어**로 다룬다. 콘텐츠와 같은 평면에서 자리를 뺏지 않는다.
- 화면당 **주요 액션은 1개**. 나머지는 시각적으로 명확히 후순위여야 한다.
- 시각적 무게(크기·굵기·색·대비) = 중요도. 이 대응이 어긋나면 무조건 수정한다.
- 콘텐츠는 화면 가장자리까지 확장하고, 컨트롤은 그 위에 떠 있게 한다.

### 2.2 Harmony (조화)
- 하드웨어의 둥근 모서리와 소프트웨어의 곡률을 맞춘다. **동심원(concentric) 라운딩**: 자식 요소의 반경 = 부모 반경 − 패딩.
- 시스템 폰트(SF Pro), 시스템 아이콘(SF Symbols), 시스템 컬러를 우선 사용한다.
- 앱 전체에서 폰트가 바뀌거나 컬러 체계가 흔들리지 않는다.
- 커스텀 컴포넌트는 "시스템 컴포넌트로 불가능함을 증명한 뒤에만" 만든다.

### 2.3 Consistency (일관성)
- 표준 동작은 표준대로 둔다. 뒤로 가기, 검색, 스와이프, 당겨서 새로고침을 재발명하지 않는다.
- 앱의 한 곳에서 배운 패턴은 다른 모든 곳에서 동일하게 동작해야 한다.
- 플랫폼 관례를 따르고, 화면 크기·기기 종류가 바뀌어도 같은 구조가 적응적으로 유지되게 한다.

### 2.4 고전 3원칙 (여전히 유효, 상위 개념)
| 원칙 | 의미 | 실무 판정 |
|---|---|---|
| **Clarity** | 어떤 크기에서도 읽히고, 아이콘은 정확하고, 장식은 미묘하다 | 텍스트를 다이내믹 타입 최대 크기로 키워도 레이아웃이 살아있는가 |
| **Deference** | UI가 콘텐츠에 자리를 양보한다 | 화면에서 UI 크롬(chrome)이 차지하는 면적이 최소인가 |
| **Depth** | 레이어와 모션으로 관계와 위계를 전달한다 | 화면 전환이 "어디서 어디로 갔는지" 공간적으로 설명되는가 |

## 3. 충돌 해소 우선순위

두 원칙이 부딪히면 **위에서부터** 이긴다.

1. **접근성·안전성** (읽을 수 없거나 조작 불가한 UI는 무조건 탈락)
2. **명료성 (Clarity)** — 예쁨보다 이해가 우선
3. **콘텐츠 우선 (Deference)** — 브랜드 표현보다 사용자 데이터가 우선
4. **플랫폼 일관성 (Consistency)** — 독창성보다 예측 가능성이 우선
5. **시각적 조화 (Harmony)**
6. 브랜드 개성·차별화

> 판정 예시: 브랜드 컬러가 대비 4.5:1을 못 맞추면 → 브랜드 컬러를 조정한다. 대비를 포기하지 않는다.

## 4. 제품 기획 방향성

에이전트가 기능을 제안하거나 스펙을 짤 때 적용한다.

### 4.1 기능 채택 기준
- **"이 기능을 빼면 핵심 목적을 달성할 수 없는가?"** 아니면 넣지 않는다.
- 파워 유저를 위한 기능이 일반 사용자의 기본 경로를 복잡하게 만들면 채택하지 않는다. 고급 기능은 숨기되 발견 가능하게 둔다.
- 새 기능은 새 화면이 아니라 **기존 흐름 안에 자연스럽게 끼워 넣을 수 있는지** 먼저 검토한다.

### 4.2 기본값 설계
- 사용자의 90%가 그대로 쓸 값을 기본값으로 정한다.
- 온보딩에서 설정을 묻지 말고, 맥락이 생겼을 때 그 자리에서 묻는다.
- 권한 요청(카메라·위치·알림)은 **앱 실행 직후가 아니라, 그 권한이 실제로 필요한 순간에** 이유와 함께 요청한다.

### 4.3 프라이버시는 기능이 아니라 전제
- 필요한 데이터만 수집한다. 수집 항목마다 "이게 없으면 무엇이 안 되는가"를 답할 수 있어야 한다.
- 가능하면 **온디바이스 처리**를 기본으로 하고, 서버 전송은 예외로 설계한다.
- 사용자에게 무엇을, 왜 쓰는지 평이한 말로 알린다.

### 4.4 접근성은 필수 요구사항
- Dynamic Type, VoiceOver, Reduce Motion, Reduce Transparency, Increase Contrast를 **출시 조건**으로 다룬다. "나중에"가 없다.
- 모든 인터랙티브 요소에 접근성 레이블을 부여한다. 아이콘 전용 버튼은 특히 필수.
- 색만으로 정보를 전달하지 않는다. 색 + 형태 또는 색 + 텍스트.

## 5. UI 구성 규칙 (수치 포함)

### 5.1 타이포그래피
- 기본 서체는 **SF Pro**(시스템 폰트). 브랜드 서체는 큰 타이틀·로고 영역에 제한적으로만.
- **Dynamic Type 필수.** 고정 pt 값을 하드코딩하지 말고 텍스트 스타일(Body, Headline, Title, Large Title 등)을 쓴다.
- 기준 크기: Body 17pt, Large Title 34pt (사용자 설정에 따라 변함 — 이 값에 레이아웃을 종속시키지 않는다).
- 본문에 11pt 미만을 쓰지 않는다.
- 한 화면의 텍스트 스타일 종류는 3~4개 이내로 제한한다.

### 5.2 레이아웃·간격
- 터치 타겟 **최소 44×44pt**. 시각적으로 작은 아이콘이어도 히트 영역은 44pt를 확보한다.
- 간격은 **4pt 배수** 체계로 통일한다 (4/8/12/16/20/24/32).
- 좌우 기본 마진은 시스템 레이아웃 마진을 따른다 (iPhone 기준 통상 16pt).
- **Safe Area를 반드시 존중한다.** 노치, Dynamic Island, 홈 인디케이터, 곡선 모서리 영역에 조작 요소를 배치하지 않는다.
- 스크롤 콘텐츠는 하단 고정 요소에 가려지지 않도록 하단 인셋을 준다.

### 5.3 컬러
- **시맨틱 시스템 컬러**를 쓴다 (`label`, `secondaryLabel`, `systemBackground`, `separator`, `systemBlue` 등). 이 값들은 라이트/다크 모드와 대비 설정에 자동 적응한다.
- 하드코딩 헥스값은 브랜드 액센트 1~2개로 제한하고, 반드시 다크 모드 대응 쌍을 함께 정의한다.
- 본문 텍스트 대비는 **4.5:1 이상**, 큰 텍스트는 3:1 이상.
- 다크 모드는 "색 반전"이 아니라 별도 설계다. 순수 검정 배경 위 순수 흰 텍스트는 피한다.

### 5.4 Liquid Glass (iOS 26+) — 절제가 핵심
Liquid Glass는 장식이 아니라 **기능 레이어를 콘텐츠에서 분리하는 재료**다.

**해야 할 것**
- 내비게이션 바, 탭 바, 툴바, 플로팅 컨트롤 등 **떠 있는 컨트롤 레이어에만** 적용한다.
- 시스템 컴포넌트를 그대로 쓰면 대부분 자동으로 적용된다. 이게 최선의 경로다.
- SwiftUI에서 직접 쓸 경우 glass 이펙트를 컨테이너로 묶어 인접 요소가 하나의 재료처럼 반응하게 한다.
- 앱 아이콘은 시스템 라이팅과 레이어 효과를 받을 수 있도록 레이어 구조로 제작한다.

**하지 말아야 할 것**
- 콘텐츠 자체(카드 본문, 리스트 셀, 텍스트 배경)에 유리 재질을 입히지 않는다.
- **유리 위에 유리를 중첩하지 않는다.**
- 투명도에 정보 전달을 의존하지 않는다. iOS 27에서 사용자가 투명도를 직접 조절할 수 있으므로, 투명도가 낮아져도 위계가 유지돼야 한다.
- Reduce Transparency / Increase Contrast가 켜졌을 때의 불투명 폴백을 반드시 구현하고 테스트한다.
- 전면 유리 배경 위에 저대비 텍스트를 올리지 않는다. 배경 콘텐츠가 무엇이든 읽혀야 한다.

### 5.5 내비게이션
- 최상위 구조는 **탭 바(2~5개)**. 6개 이상이면 정보 구조 자체가 잘못된 것이다.
- 계층 이동은 내비게이션 스택(푸시), 독립 작업은 모달(시트).
- **모달은 흐름을 끊는 장치다.** 반드시 끝내야 하는 작업에만 쓰고, 항상 명확한 취소·닫기 경로를 준다.
- 탭 전환 시 각 탭의 상태를 보존한다. 활성 탭을 다시 탭하면 해당 탭의 최상단으로 돌아간다.
- 뒤로 가기는 스와이프 제스처를 포함해 시스템 동작 그대로 유지한다.

## 6. 인터랙션과 모션

- **직접 조작감**: 사용자가 데이터를 "명령"하는 게 아니라 "만지는" 느낌이어야 한다. 드래그·핀치·스와이프는 손가락을 실시간으로 따라간다.
- 모든 액션에 **즉각적 피드백**(시각·햅틱·사운드 중 하나 이상)을 준다. 응답이 100ms를 넘으면 상태를 보여준다.
- 모션은 **의미를 전달할 때만** 쓴다. 어디서 왔고 어디로 가는지 설명하는 전환은 좋고, 눈길을 끄는 장식 애니메이션은 나쁘다.
- 전환은 인터럽트 가능해야 한다. 애니메이션이 끝날 때까지 사용자를 기다리게 하지 않는다.
- **Reduce Motion**이 켜지면 시차·확대 전환을 크로스 페이드로 대체한다.
- 햅틱은 의미 있는 순간에만. 남발하면 신호가 소음이 된다.

## 7. 기술 방향성

- **SwiftUI 우선.** SwiftUI 기본 컴포넌트를 쓰면 HIG 준수, 다이내믹 타입, 다크 모드, 접근성, Liquid Glass 적응을 상당 부분 무료로 얻는다. 커스텀으로 갈수록 이 이점을 잃는다는 걸 인지하고 결정한다.
- 필요한 곳에서만 UIKit과 상호운용하고, 두 체계를 뒤섞은 하이브리드 UI는 최소화한다.
- **성능은 UX다.** 스크롤은 60fps(ProMotion 기기 120fps)를 유지한다. 블러·유리 효과는 GPU 비용이 크므로 리스트 셀마다 적용하지 않는다.
- 실행 직후 첫 화면에 유의미한 콘텐츠를 그린다. 스플래시로 시간을 벌지 않는다.
- 네트워크 실패, 권한 거부, 빈 상태, 로딩 상태를 **화면 설계 단계에서 함께 정의한다.** 이 4가지 상태가 없는 화면 명세는 미완성으로 간주한다.
- 온디바이스 프레임워크(Vision, Core ML, Speech 등)를 우선 검토한다. 서버 왕복 없이 되는 일은 서버로 보내지 않는다.
- 지역화(localization)를 전제로 문자열을 분리하고, 텍스트 길이가 1.5배가 되어도 레이아웃이 깨지지 않게 한다.

## 8. 라이팅

- 버튼 라벨은 **동사**로. "다음", "저장", "결제하기" — 결과를 예측할 수 있게.
- 영리하거나 귀여운 표현보다 명확한 표현. "자, 시작해볼까요!"보다 "시작".
- 1인칭/2인칭을 하나만 골라 앱 전체에서 유지한다.
- 오류 메시지는 (1) 무슨 일이 일어났는지, (2) 사용자가 무엇을 하면 되는지를 담는다. 에러 코드만 던지지 않는다.
- 빈 화면에는 반드시 다음 행동을 안내한다.
- 전문 용어와 내부 용어를 노출하지 않는다.

## 9. 안티패턴 (발견 즉시 수정)

- 시스템 뒤로 가기·스와이프 동작을 커스텀으로 대체
- 스플래시 화면에 브랜드 애니메이션 3초
- 앱 진입 직후 전면 권한 요청 팝업 연속 노출
- 44pt 미만 터치 타겟
- 하드코딩된 폰트 크기 (다이내믹 타입 미지원)
- 색상만으로 상태 구분 (에러=빨강만, 성공=초록만)
- 유리 위 유리, 콘텐츠 영역 전면 유리 처리
- 장식 목적의 시차·바운스 애니메이션
- 다크 모드 미지원 또는 단순 색 반전
- "설정에서 바꿀 수 있어요"로 해결한 나쁜 기본값
- 한 화면에 동등한 무게의 CTA 2개 이상
- 아이콘 전용 버튼에 접근성 레이블 없음

## 10. 코드 판정 예시

```swift
// ❌ 나쁨: 고정 크기, 하드코딩 컬러, 작은 터치 타겟, 유리 남용
Text("결제")
    .font(.system(size: 14))
    .foregroundColor(Color(hex: "#333333"))
    .frame(width: 32, height: 28)
    .glassEffect()

// ✅ 좋음: 다이내믹 타입, 시맨틱 컬러, 44pt 히트 영역, 시스템 컴포넌트
Button("결제하기") { pay() }
    .font(.headline)
    .foregroundStyle(.primary)
    .frame(minWidth: 44, minHeight: 44)
    .buttonStyle(.borderedProminent)
    .accessibilityLabel("결제하기")
```

> API 시그니처(`glassEffect`, `GlassEffectContainer`, 버튼 스타일 등)는 대상 SDK 버전에서 실제 이름을 확인하고 쓴다. 확실하지 않으면 시스템 기본 스타일을 쓴다.

## 11. 산출물 자가 검증 체크리스트

산출물을 내놓기 전 전부 통과해야 한다.

**위계**
- [ ] 이 화면의 주요 액션이 1개로 명확한가
- [ ] 시각적 무게 순서 = 중요도 순서인가
- [ ] 컨트롤과 콘텐츠가 레이어로 분리되어 있는가

**조화·일관성**
- [ ] 시스템 폰트·아이콘·컬러를 쓰고 있는가
- [ ] 커스텀 컴포넌트마다 "시스템으로 불가능한 이유"를 댈 수 있는가
- [ ] 표준 제스처와 내비게이션 동작을 그대로 유지했는가
- [ ] 라운딩이 부모–자식 간 동심원 규칙을 따르는가

**접근성**
- [ ] Dynamic Type 최대 크기에서 레이아웃이 살아있는가
- [ ] 모든 터치 타겟이 44×44pt 이상인가
- [ ] 본문 대비가 4.5:1 이상인가
- [ ] Reduce Motion / Reduce Transparency 대응이 있는가
- [ ] VoiceOver로 전체 플로우를 완주할 수 있는가
- [ ] 색 없이도 정보가 전달되는가

**상태**
- [ ] 로딩 / 빈 상태 / 오류 / 권한 거부 4가지가 모두 정의되었는가
- [ ] 오류 메시지가 다음 행동을 알려주는가

**Liquid Glass**
- [ ] 유리를 기능 레이어에만 썼는가
- [ ] 유리 중첩이 없는가
- [ ] 투명도가 꺼져도 위계와 가독성이 유지되는가

**Safe Area·성능**
- [ ] Safe Area 밖에 조작 요소가 없는가
- [ ] 스크롤 시 프레임 드랍을 유발할 효과가 반복되지 않는가
